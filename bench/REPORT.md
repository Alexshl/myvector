# myvec bench: вибір embedding-моделі та налаштувань sqlite-vec

Дата прогону: 2026-11-03. Машина: Apple M5 Pro, 24 GB, Ollama (GPU), sqlite-vec 0.1.9, SQLite 3.50.4, Python 3.12.
Усі скрипти та команди для відтворення: [`README.md`](README.md). Сирі дані: `results/*.json`, `results/per_query.csv`.

## 1. Висновок (коротко)

| Рішення | Вибір | Обґрунтування |
|---|---|---|
| Модель | **`embeddinggemma`** (Ollama) | Найкращі recall/MRR серед трьох, найшвидша індексація (~34-38 chunks/s проти 12-17) і найшвидший embedding запиту (9 мс). Але різниця з `bge-m3` статистично не значуща (n=45, див. розд. 5). |
| Резервна модель | `bge-m3` | Така сама в hybrid-режимі (R@10 0.889 обидві), контекст 8k токенів, але ~2.5x повільніша індексація. |
| Не брати | `qwen3-embedding:0.6b` | Найгірша на цьому наборі (R@10 0.73) і найповільніша індексація (~13-14 chunks/s). Можливо, це артефакт Ollama/префіксу, а не моделі (див. розд. 5). |
| Розмірність | **768** (повна). 512 (MRL-усічення) допустимий як опція | 768 -> 512: R@10 0.911 -> 0.889, MRR 0.606 -> 0.563 (у межах шуму), зате вдвічі менше сховища і ~1.8x швидший скан. Для qwen3 усічення 1024 -> 512 майже нічого не коштувало (0.733 -> 0.711). |
| Режим пошуку | **hybrid (vector + FTS5 unicode61, RRF k=60)** з простим роутингом: запит без пробілів (ідентифікатор) -> hybrid, природна мова -> vector | Hybrid дає +0.20 R@10 на ідентифікаторах (0.80 -> 1.00), але на природній мові RRF з OR-запитом FTS трохи шкодить (gemma-768: semantic R@10 0.943 -> 0.857). Роутинг дає R@10 0.956, MRR 0.643 (але це in-sample, див. розд. 4). |
| FTS-токенайзер | `unicode61 remove_diacritics 2` | trigram не дав переваги (hybrid R@10 0.867 vs 0.889), а індекс у 2.2x більший (235 MB vs 105 MB на 30k chunks). |
| sqlite-vec, зберігання | float32 + `partition key` по проєкту/scope | Запит в одному scope: 3-20 мс навіть при 200k-1M рядків у таблиці. |
| sqlite-vec, крос-проєктний пошук | float32 full scan до ~100k chunks (<= ~100 мс при 512d); вище - `bit[]` coarse top-500 + float32 rescoring | bit+rescore майже без втрат (overlap з точним top-10: 0.996-1.000 на реальних векторах) і 2.3x швидше на 1024d. `int8` - лише якщо критична пам'ять: втрачає 6-8% top-10 (overlap 0.92-0.94). |
| Бюджет виводу | **~1.5-2k токенів на відповідь**: 10 хітів у вигляді `path:рядки` + 3 рядки (~550 токенів), і лише top-3 розгорнути до ~25 рядків (~900 токенів) | Top-5 цілих chunks = ~2.7-3.0k токенів (chunk = 60 рядків, ~2000 симв., ~500 токенів); у вигляді path + 3 рядки - лише ~250-280 токенів. R@10 помітно вищий за R@5 (0.91 vs 0.82), тому краще показувати 10 коротких хітів, ніж 5 довгих. |

## 2. Методика

**Корпус** (read-only, `git ls-files`): `project-b/site`, `project-b/maximus-libs`, `project-b/ocr`, `project-d.se/public_html`, `project-g`.
Виключено: vendor, node_modules, dist, build, templates_c, graphify-out, `*.min.*`, lock-файли, бінарні, файли > 1 MB, `.env*`, імена з `password`/`secret`, `*.sql`, `*.pem`, `*.map`.
Сирих chunks 37 741; для ліміту ~30k великі репозиторії (`project-b/site`, `project-d.se`, `project-g`) семплювались випадково по файлах (seed 42), малі (`maximus-libs`, `ocr`) - повністю; файли з golden set завжди включені. Підсумок: **30 233 chunks**, 61 MB тексту (середній chunk 2029 симв., ~500 токенів). Chunking: вікно 60 рядків, overlap 10, перед текстом - відносний шлях; chunk обрізаний до 3000 симв. Той самий chunking для всіх моделей.
Корпус включає тести, документацію (`docs/`, `*.md`) і фронтенд, тобто реалістичну "кашу" проєктів.

**Golden set** (`golden.jsonl`, 45 запитів): 35 semantic (13 uk, 10 ru, 12 en; поведінка без ідентифікаторів з коду) + 10 identifier (точні назви функцій/класів/констант/конфіг-ключів). Розподіл по репо (semantic + identifier): site 11 + 2, maximus-libs 4 + 2, ocr 5 + 2, project-d 6 + 2, project-g 9 + 2. Expected - рівень файлу (1-2 файли на запит).

**Моделі** (Ollama `/api/embed`, батчі по 32): qwen3-embedding:0.6b (запит з `Instruct: ...\nQuery: `; повні 1024 і MRL-усічення до 512 з L2-ренормалізацією), bge-m3 (без префіксів), embeddinggemma (`task: search result | query: ` / `title: none | text: `; 768 і MRL 512 як додатковий варіант).

**Режими**: `vector` (sqlite-vec vec0, `distance_metric=cosine`, k=50); FTS5-only (BM25, top-50; для semantic запитів слова довжиною >= 3 з'єднані через OR, для identifier - фраза); `hybrid_u` = RRF(k=60) від vector top-50 і FTS unicode61 top-50; `hybrid_t` - те саме з trigram; `hybrid_ut` - три списки (vector + обидва FTS); `ripgrep` - `rg -c -i` з альтернацією слів довжиною > 3 по кожному репо, файли за кількістю збігів (обмежено файлами корпусу).
**Метрики**: chunks дедупліковані до файлів за порядком рангу; recall@5, recall@10 (частка expected-файлів у top-k), MRR (по першому expected-файлу).

## 4. Hybrid проти vector-only

- **Загалом** (gemma-768): hybrid_u не краще vector: R@10 0.889 vs 0.911, MRR 0.582 vs 0.606 (різниця = 1 запит; шум). Для bge-m3 hybrid кращий: R@10 0.889 vs 0.822 (+0.067), MRR +0.017. Для qwen3 - без різниці.
- **Ідентифікатори**: hybrid стабільно виправляє vector: R@10 0.80-0.90 -> 1.00, MRR для gemma 0.665 -> 0.833. Тобто hybrid потрібен для "знайти функцію за назвою".
- **Природна мова uk/ru**: FTS додає шум; найкраще працює чистий vector.
- **Висновок**: hybrid виграє там, де є точні токени; на uk/ru NL-запитах краще vector. Дешевий роутер (запит без пробілів -> hybrid, інакше vector) на цьому наборі дає R@10 0.956 (95% CI 0.89-1.00), MRR 0.643. Це **in-sample** оцінка: правило сформульоване після перегляду набору, тому реальний виграш менший. Не перевірено: зважений RRF (менша вага FTS для NL), стоп-слова/стемінг для uk/ru.
- `ripgrep` на ідентифікаторах не поступається FTS (R@10 0.95), але на semantic дає 0 (як і очікувалось), ~300 мс на запит по 5 репо.

## 5. Чесні застереження

1. **Golden set написаний ШІ, який читав код.** Запити перефразують docblock-коментарі та логіку конкретних файлів, тому вони упереджені в бік "знаходимого": формулювання семантично близькі до коментарів, а не до того, як людина, що забула деталі, формулює запит. Реальні запити будуть гіршими й розмитішими. Абсолютним значенням recall довіряти не можна, лише порівнянню варіантів.
2. **Мала вибірка** (45 запитів, 1 запит = 2.2 п.п.). Bootstrap 95% CI для R@10 gemma-768 vector: 0.82-0.98; bge-m3 vector: 0.71-0.93. Парна різниця gemma-768 мінус bge-m3 (R@10, vector) = +0.089, CI [-0.044; +0.222] - **включає 0**. Тому "gemma кращий за bge-m3" не доведено; доведено лише, що qwen3 у нашій конфігурації помітно слабший (R@10 0.73, CI 0.60-0.87).
3. **Expected = лише файл-визначення.** Тести, виклики та документація, що теж релевантні, рахуються промахами. Це занижує абсолютні числа (особливо MRR для ідентифікаторів: тести з тим самим ім'ям ранжуються вище).
4. **Семплінг корпусу**: у великих репо ~20% файлів відкинуто, але файли golden set завжди в корпусі. Дистракторів трохи менше, ніж у повному індексі; реальний recall нижчий.
5. **qwen3-embedding:0.6b міг постраждати від особливостей Ollama** (пулінг/EOS, формат інструкції, квантизація GGUF). Перевірено лише, що додавання `<|endoftext|>` майже не змінює вектор (cos 0.997). Не стверджую, що модель погана взагалі, лише що в цьому стеку вона не виправдовує вартість.
6. **embeddinggemma має контекст 2048 токенів** (Ollama обрізає довші входи); chunks <= 3000 симв. здебільшого вміщуються, але довгі рядки можуть обрізатись. Також варто перевірити умови ліцензії Gemma.
7. **Латентності та throughput виміряні на не-ізольованій машині** (паралельно працювали інші агенти, OrbStack, Claude app; load average 5-14). Числа - верхні оцінки, p95 шумні.
8. **Квантизація перевірена на реальних векторах лише qwen3** (gemma/bge-m3 не прогонялись); на випадкових векторах overlap з точним top-k не інформативний (вектори майже ортогональні), тому його не наводжу (є в `loadtest.json`).
9. Фіксований chunking (60/10) не оптимізовано під модель; AST-chunking може змінити картину.

### 6.5. sqlite-vec load test (синтетика, нормалізовані випадкові вектори, k=50, p50 / p95 мс)

| rows x dims | f32 full scan | f32 partition key (1 з 100) | int8 | bit top-500 + f32 rescoring | з них bit coarse (p50) | розмір f32 / int8 (MB) |
|---|---|---|---|---|---|---|
| 50k x 512 | 31.6 / 48.0 | 3.9 / 8.3 | 21.0 / 31.2 | 19.1 / 21.1 | 18.5 | 104 / 27 |
| 200k x 512 | 120.9 / 163.3 | 3.3 / 6.5 | 76.4 / 89.8 | 103.6 / 116.4 | 65.3 | 416 / 107 |
| 1M x 512 | 2368 / 3386 | 20.3 / 28.3 | 449 / 499 | 404 / 511 | 336.9 | 2076 / 536 |
| 200k x 1024 | 239.7 / 284.9 | 4.3 / 4.9 | 145.7 / 175.8 | 102.3 / 119.2 | 65.1 | 828 / 210 |

Час побудови індексу, с: 1M x 512 - f32 19, partition 185, int8 6, bit 21 (partition key будується помітно довше).
Якість квантизації на реальних qwen3-векторах (overlap із точним float32 top-k, 45 запитів, 30k chunks): int8 - 0.924 (512d) / 0.938 (1024d) @10; bit coarse top-500 -> float32 rescoring - 0.996 / 1.000 @10, 0.959 / 0.987 @50; bit без rescoring - лише 0.56-0.68 @10 (непридатно).

**Чи достатньо brute force для ~200k chunks на scope?** Так, для інтерактивного використання: float32 full scan при 512d = 121 мс p50 (163 p95), при 1024d = 240 мс (для 768d інтерполяція дає ~180 мс). Це вкладається в бюджет "відповідь < 0.5 с", але не "миттєво". На 1M рядків full scan вже непридатний (2.4 с). Варіанти:
- Scoped-пошук (один проєкт / тип нотаток): `partition key` -> 3-5 мс при 200k і 20 мс при 1M у таблиці. Ціна: побудова в 5-10 разів довша і те, що запит поза scope = сканувати кожну партицію окремо (100 x ~3 мс ~ 300 мс), тобто крос-проєктний пошук краще робити по нерозбитій таблиці (full scan або bit+rescore).
- Крос-проєктний пошук > ~100k chunks: bit[] coarse top-500 + rescoring float32. Виграш помітний для 1024d (102 vs 240 мс); на 512d при 200k він мізерний (104 vs 121 мс), бо rescoring 500 рядків через `IN (...)` коштує ~35-40 мс (ймовірно, можна прискорити, роблячи rescoring в застосунку; не перевірялось). Потребує зберігати float32-вектори поряд.
- int8: 1.4-1.6x швидше за f32 на 50k-200k і ~5x на 1M, 4x менше пам'яті, але втрачає 6-8% точного top-10. Не рекомендую, якщо пам'ять не критична.
- На очікуваних обсягах myvec (десятки тисяч chunks на scope) квантизація не потрібна: f32 + partition key достатньо.

## 7. Що не зроблено / обмеження

- Не тестувався зважений RRF, стоп-слова, стемінг для uk/ru, AST-chunking, reranker.
- Квантизація на реальних векторах - лише qwen3 (не gemma/bge-m3).
- Чистих (ізольованих) вимірів латентності/throughput немає (див. розд. 5, п. 7).
- 1M x 1024 не запускався (за ТЗ тільки 200k x 1024).
- Оцінка 768d для 200k (~180 мс) інтерпольована, а не виміряна.
- Правило "adaptive" оцінене на тому ж наборі, на якому сформульоване.
