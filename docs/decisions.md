# Рішення (ADR)

## ADR-001 MyVector PM: тікети й сесії всіх проєктів і нод

2026-11-09, грильня з власником. Епіки E1–E5 у `docs/todo`.

**Проблема.** Тікети в кожному проєкті в іншому форматі (YAML, таблиці, жирні рядки, один todo.md); ніде не записано, яка сесія що робить; сесії, що чекають відповіді, губляться внизу списку.

**Рішення.**
- **Джерело істини** — md-файли тікетів у git проєкту. myvec лише індексує (watcher), проєкти нічого не «надсилають».
- **Формат** — канон v1 з YAML-шапкою (`id, title, kind, status, parent, size, deps, blocks, branch, pr, summary, updated`), регламент у skill `/myvector`. Старі проєкти переводить агент проєкту (`myvec ticket migrate`); непереведені в трекері не показуються.
- **Дерево** — `parent` будь-якої глибини; розділ — тікет `kind: group`; відсоток групи — середнє дітей.
- **Статуси** — todo, in_progress, review, waiting, blocked, partial, done, cancelled, frozen; емодзі — синоніми. Відсоток листа: done 100, partial/in_progress — за чекбоксами Acceptance criteria.
- **Сесії** — хуки Claude Code (SessionStart, UserPromptSubmit, Stop, Notification, PreToolUse AskUserQuestion). Прив'язка до тікета за гілкою `t/<id>-…` або `myvec ticket claim`. Стани: працює / чекає на тебе / затихла (>15 хв) / завершена.
- **Відновлення** — через claude-manager: жива cm-сесія → `cm send`; мертва → `cm resume` + `cm send`; зайнята звичайним терміналом → кнопка неактивна, копіюється форк. Плюс копіювання UUID, команди й тексту для сесії manager.
- **Коментарі з UI** — файл `docs/todo/inbox/<дата>-<id>.md` в основному checkout (у .gitignore); нода тікет не редагує; оркестратор переносить у `## Comments`/Log і видаляє файл.
- **Рекомендації** — регламент + CLI + тікети у векторному пошуку + аналіз здоров'я; власної LLM немає.
- **Хмара** — Cloudflare Worker (`cloud/`, D1 + Durable Object) на pm.example.com. Нода тримає вихідний WebSocket (HTTP-фолбек снапшотом). Назовні йдуть лише тікети (через маскування `filters.py`) і сесії; код, вектори, пам'ять — ні. З хмари в ноду — лише білий список дій. Вхід — Cloudflare Access, ноди — bearer-токен.
- **Кілька нод** — проєкт ідентифікується git remote (одна картка, свіжіші тікети, позначка розбіжності); без remote — «нода + шлях».
- **UI** — один модуль трекера на vanilla JS з `src/myvec/ui`: локально (своя нода) і в Worker (усі ноди).

**Порядок.** E1 тікети локально → E2 сесії → E6 моніторинг (ADR-003) → E3 inbox і здоров'я → E4 хмара → E5 міграція (project-a → project-b → project-c.lv). Макети UI затверджує власник до коду; деплой у хмару — лише за його згодою.

## ADR-002 Канон тікета v1: парсер, емодзі, відсоток

2026-11-09, planner E1-01.

- **YAML** — власний парсер підмножини в `src/myvec/tickets.py` (скаляри, лапки, inline- і блочні списки, `>`/`|`); PyYAML не додаємо: шапки плоскі, залежність зайва для демона й обох машин. Непідтримане → issue, не мовчки.
- **Емодзі** нових статусів: ⏳ waiting (загальне «чекає»), 🟧 partial (родина квадратів ⬜🟦🟨; 🟩 відкинуто — схожий на ✅). ❄ приймається з `U+FE0F` і без.
- **Відсоток листа** (рішення оркестратора): done = 100, todo = 0, cancelled виключається із середнього батька (скасований обсяг не робота); усі інші (in_progress, review, waiting, blocked, partial, frozen) — частка відмічених чекбоксів Acceptance criteria (без AC → 0). Review не 0%: робота майже зроблена. Група — рівне середнє дітей, без ваги розміру; група без врахованих дітей — за власним статусом.
- **Перехід**: `epic:` без `parent` читається як `parent`; `index.md` теки `E<id>-<slug>` без `id` — синтетична група. Підтримка знімається після міграції проєктів (E5).


## ADR-003 Моніторинг навантаження й тестів

2026-11-09, рішення власника.

**Проблема.** Тести проєктів часом з'їдають величезну кількість процесорного часу. На devbox (стоїть окремо) цього не чути й не видно; для оптимізації тестів бракує цифр.

**Рішення.**
- **Заміри тестів двома шляхами.** Точно — обгортка `myvec measure [--ticket] [--agent] -- <команда>`: дерево процесів, wall- і CPU-час (user+sys), середній/піковий CPU%, пік RSS, код виходу; рядок-зведення для звіту й запис у БД. Пасивно — семплер демона впізнає прогони тестів за командним рядком (pytest, phpunit, artisan test, vitest, jest, npm test) і без обгортки. Залежність psutil.
- **Регламент.** tester і qa ганяють тести через `myvec measure` і вставляють зведення в Log тікета й звіт.
- **Навантаження ноди.** Кожні 5 с: CPU (усього й по ядрах), load average, пам'ять, температура CPU (якщо доступна), CPU процесів з розподілом по проєктах за cwd. Зберігання: сирі 24 год, хвилинні агрегати 30 днів, прогони тестів — безстроково. У хмару — лише хвилинні агрегати й прогони.
- **Тривоги.** CPU > 85% довше 5 хв (пороги в config) → банер у UI і в хмарі з проєктом і процесом. Прогін на 25% довший або дорожчий за CPU, ніж медіана останніх 10, — регресія. Процеси автоматично не вбиваємо.
- **UI.** Розділ «Навантаження» (графіки ноди, топ проєктів, поточні прогони) і вкладка проєкту «Тести» (історія прогонів, тренд). Епік E6 — після E2, перед E3.

E2-02 читає через `read_claims()` або переносить у таблицю `sessions`; CLI не міняється. Session id за замовчуванням з env `CLAUDE_CODE_SESSION_ID`.

- **`log`** проганяє текст через `filters.mask_secrets` і відмовляє при `has_hard_secret`.

## ADR-005 Тікети в БД і в пошуку

2026-11-09, planner E1-02.

- **Пошук — без окремого джерела.** Файл тікета індексується як звичайний markdown-чанк (ті самі фільтри, ембеддинги, RRF). Позначка «тікет» (`hit.data.ticket`: проєкт, id, статус) додається при видачі join-ом абсолютного шляху хіта з таблицею `tickets`. Відкинуто: окремі `ticket_chunks`/`tickets_vec` (дубль ембеддингів, новий список у RRF, переганяння bench, reembed) і маркер у `chunks` (чанки content-addressed і спільні між проєктами/гілками, а «тікет» — властивість шляху).
- **БД трекера — окремі похідні таблиці** `tickets`, `ticket_edges`, `ticket_issues`, `ticket_dirs` (схема v5), ключ `project_path`; повна заміна рядків проєкту в одній транзакції. Джерело істини — файли, `rebuild` відновлює.
- **Оновлення без sync.** Відбиток теки (`stat` `*.md` + `tickets_dir`); демон на подію watcher під тікет-текою оновлює таблиці через 1,5 с в окремому потоці без `sync_lock` і ембеддера; `sync_project` теж викликає оновлення (CLI, rebuild, safety); раз на 5 хв — rescan усіх проєктів, зокрема неактивних.
- **Секрети.** `title/summary/body` через `mask_secrets`; тіло з hard secret не зберігається; файли за `is_denied_path` пропускаються. Це те, що піде в хмару (E4).
- **Тека** — `[tickets] dir` у `.myvector.toml` (дефолт `docs/todo`), невалідна → дефолт + warning, проєкт не ламається. Тікети читаються з робочого дерева кореня проєкту (не з інших гілок/worktree).

## ADR-007 Сесії: журнал подій хуків і автомат станів

2026-11-09, planner E2-01.

- **Хук не пише в БД.** Кожен хук сесії додає один рядок JSONL (`O_APPEND`, ≤ 4 КБ, `0600`) у `MYVEC_HOME/state/session_events.jsonl`; демон раз на тік (1 с) забирає журнал атомарним rename і складає в таблицю `sessions` (схема v6), він — єдиний писач. Відкинуто: пряме SQLite з busy timeout, як `activity.touch` — sync тримає запис, тоді потрібен другий шлях (фолбек-файл), і порядок подій розходиться. Без демона журнал складає `myvec sessions`. Журнал без демона обмежений 20 МБ: понад це хук не пише пульси (події, що міняють стан, пишуться).
- **Події:** SessionStart, UserPromptSubmit, Stop, Notification, SessionEnd, PreToolUse і PostToolUse з matcher `AskUserQuestion`; наявний post-edit — пульс `last_seen`. SessionEnd додано до списку ADR-001: без нього «завершена» не визначається. Хуки синхронні (`async` ламає порядок), `timeout: 10`, вихід завжди 0.
- **Стани:** `working` (промпт, відповідь на питання, Stop з фоновими задачами), `waiting` — «чекає на тебе» (старт, Stop, AskUserQuestion з текстом, Notification permission/idle/elicitation/agent_needs_input), `ended` (SessionEnd; наступна подія відкриває знову), `idle` — «затихла»: `working` без подій довше `session_idle_minutes` (15) — обчислюється при читанні. `waiting` не затихає: саме такі сесії губляться. Пульс (PostToolUse `*`, async) оновлює лише `last_seen`, стан не міняє. Окреме поле `last_state_event_at` рухають тільки події, що міняють стан; запізніла стара подія стан не відкочує, `idle` рахується від нього. Події субагентів (`agent_id`) стан не міняють. Завершені сесії видаляються через `session_retention_days` (30). Ключі config: `session_idle_minutes`, `session_retention_days`.
- **Приватність:** текст промпту не зберігається; питання й хвіст останньої відповіді — через `mask_secrets`, hard secret → `NULL` (це піде в хмару, E4).
- **Похідність:** `sessions` — стан виконання, не з vault; після `rebuild` живі сесії з'являються з наступною подією. `ticket_id/ticket_source` зарезервовані для E2-02.

## ADR-009 Прив'язка сесії до тікета обчислюється при читанні

2026-11-09, planner E2-02.

- **Обчислення при читанні, не колонка.** `list_sessions`/`by_ticket` на кожен виклик читають `ticket_claims.jsonl` (ADR-004) і id тікетів із `tickets`, тож прив'язка не застаріває: claim видно без події хука, новий тікет підхоплюється, «чекаюча» сесія без подій теж прив'язана. Схема лишається v6; колонки `ticket_id/ticket_source` (ADR-007) не пишуться. Відкинуто запис у `fold()`: потрібні подія `claim` у журналі сесій і перерахунок усіх сесій при зміні тікетів, дві копії істини.
- **Пріоритет:** claim (`ticket_id` не null) > гілка `t/<id>[-…]` > worktree `…/.worktrees/<id>`. `<id>` — найдовший id, що існує в тікетах проєкту (`E1-02`, не `E1`); невідомий id автоприв'язки не дає. `--release` повертає автоприв'язку.
- **Проєкт:** сесії — `project_of(cwd, worktree, головний корінь worktree)`; головний корінь linked worktree береться з `.git`-файлу і `commondir` без git-процесу. Тікет claim шукається в проєкті `project_root` запису claim.
- **Вивід:** `ticket_project, ticket_id, ticket_source, ticket_title, ticket_status` у рядках сесій; `sessions` у вузлах `project_tickets` і в `get_ticket`. E4, якщо знадобиться колонка в хмарі, обчислює ті самі поля при вивантаженні.

## ADR-010 Відновлення сесії з UI через `cm`

2026-11-09, planner/docs-writer E2-05.

- **Обгортка `src/myvec/cmctl.py`:** лише `subprocess.run([...], shell=False)` з `cm_path` (config, типово `~/.local/bin/cm`) і таймаутом `cm_timeout_s`; stdout/stderr у відповідь тільки хвостом ≤ 300 символів через `mask_secrets`. Текст відповіді йде **через stdin** (`cm send <id> -`), не в argv: його не видно в `ps`/`/proc/*/cmdline`.
- **Feature-detect:** `cm send --help` / `cm who --help`, `--wait` у виводі; кеш можливостей TTL 60 с (не за mtime шима: editable `cm` не міняв mtime після `cm update`). Нема можливостей -> `unavailable`, кнопки копіювання працюють. `cm ls` кешується 10 с.
- **Режим** — чиста `sessionact.decide(who, row, caps)`: `send` (керована, жива), `restart_send` (керована, мертва), `held` (некерована, є чужий holder), `resume_send` (некерована, вільна), `unavailable`. У списках `approx_who` бере один `cm ls`; **`held` — лише коли процес із точним session id в аргументах (`cmctl.process_session_ids` через `ps`)**, не за cwd і не за станом хуків. POST завжди перевіряє авторитетно через `cm who`.
- **POST** `/api/sessions/{sid}/resume` `{text}`: `GuardMiddleware`, sid за UUID (`fullmatch`) і наявність у `sessions`, текст ≤ 16000 без керівних символів (крім `\n`/`\t`); порожній текст = лише відновити. Пер-сесійний lock (`WeakValueDictionary`, non-blocking) -> 409. Мапінг: 400 поганий sid/текст, 404 невідома сесія, 409 `held`/`busy` (код 4 від `cm send`)/`dead`/дія вже йде, 502 помилка cm (зокрема `cm who` з ненульовим кодом), 503 cm недоступний. Якщо restart/resume вдався, а send дав 4 - повідомлення каже, що сесію відновлено. У `bus` — `session_action` (`session_id, action, exit_code, ok, text_len`); тексту відповіді ніде нема.
- **`cm restart`/`cm resume` зберігають session_id** (новий лише з `--fork`), тож прив'язка до тікета не рветься.
- **Шов для E3:** `sessionact.on_answer(project, ticket_id, session_id, text)` — сьогодні no-op; E3 пише inbox (ADR-001).

## ADR-011 `myvec measure`: як міряємо й куди пишемо

2026-11-09, planner E6-02; уточнено docs-writer за реалізацією.

- **CPU-час: `os.wait4` + psutil, береться більший.** `wait4` дає точний user+sys дитини разом з нащадками, яких вона дочекалася (xdist, paratest), зокрема тих, що вийшли між семплами; psutil накопичує CPU за ключем `(pid, create_time)`. `cpu_s = max(wait4, семплер)` (осиротілі нащадки, яких ніхто не дочекався, потрапляють лише у семплер). Піки ядер — дельти `cpu_times` між семплами (перший побачений pid — базова лінія), інтервал 1 с. Пік пам'яті — сума по дереву **USS** (`memory_full_info`, спільні сторінки раз; PSS не використовується), при `AccessDenied` — RSS; без жодного семпла — `ru_maxrss` дитини. Без psutil піки `null`. Відкинуто: лише psutil (втрачає процеси між семплами), лише stdlib (нема піків на Mac).
- **Таблиця `test_runs` (схема v7)** для обох джерел (`source = wrapper|passive`), стан `running → done|lost`; рядок `running` з `pid` — для «поточних прогонів» і дедупу пасивного детектора (E6-03). Колонка `interrupted` (0/1): прогін перервано сигналом (у зведенні «· перервано»). Тікет фіксується на момент запуску (на відміну від сесій, ADR-009). Не похідна від vault: `rebuild` її не відновлює, як і `sessions`.
- **Без блокувань:** пряма вставка з `busy_timeout` 300 мс, інакше (locked, нема БД/схеми) — журнал `state/test_runs.jsonl` (подія ≤ 4 КБ одним `O_APPEND`-записом, upsert за `run_uid`), який фолдить демон (тік) і наступний `measure`; `running` на цьому хості з мертвим `pid` старше 1 хв стає `lost`. Обгортка ніколи не міняє код виходу через БД; сигнал N → 128+N.
- **Сигнали:** хендлери ставляться до `Popen`; SIGTERM/SIGHUP пересилаються дитині одразу, SIGQUIT після `Popen` ігнорується (дитина не успадковує). SIGINT пересилається лише коли обгортка не на передньому плані tty (`tcgetpgrp == getpgrp`): з терміналу Ctrl+C уже отримала вся група, повторна пересилка дала б дитині два SIGINT. Обмеження: `kill -INT <обгортка>` з іншого шела, поки обгортка на передньому плані terminal-групи, не пересилається. Після завершення сигнал перепіднімається на собі.
- **Швидкий шлях у `cli.py`** до імпорту typer (як `hook`). Команда, `agent` і `label` маскуються `filters.mask_secrets`, з hard secret — `[команда приховано]`.

## ADR-012 Семплер навантаження ноди

2026-11-09, planner/coder E6-01.

- **Окремий потік `myvec-sampler`** у демоні, власний таймер на `monotonic` (`load_sample_s`, 5 с), не тік демона. Знімки в пам'яті (кільце 720); запис пакетом раз на хвилину (сирі + хвилинний агрегат однією транзакцією). БД зайнята - буфер лишається (кеп 30 хв), спроба наступної хвилини; втрата при падінні ≤ 1 хв. Слухач (`Sampler.add_listener`, хук для E6-03) не може зламати семплер.
- **Окрема БД `~/MyVector/load.db`** (не `index.db`): не роздуває індекс і не конкурує з sync за запис; власна схема (`meta.schema_version = 1`, `CREATE IF NOT EXISTS`), не похідна від vault. Колонка `host` у всіх таблицях - для вивантаження в хмару (E6-08). Таблиці: `node_samples`, `node_proc_samples` (рядки ≥ 0,5% ядра + «інше»), `node_minutes`, `node_proc_minutes`. Ретеншн (сирі `load_raw_hours` = 24, хвилини `load_minutes_days` = 30) - при записі не частіше разу на 10 хв.
- **Процеси:** кожен знімок читає лише `cpu_times` усіх (дельта за `(pid, create_time)`, перший побачений pid - базова лінія). `cwd` - лише для процесу з ненульовою дельтою, раз на `(pid, create_time)`; проєкт - найглибший зареєстрований root, що містить cwd, або головний checkout linked worktree (`main_root_of`, без git-процесу); непризначений cwd - проєкт батька, якщо він уже в кеші, інакше «інше». `AccessDenied`/зниклий процес - «інше»; «інше» = CPU ноди − сума проєктів, не менше 0. Накладні ≈ 0,3% ядра при 5 с (замір devbox, 571 процес); повний прохід із `cwd` для всіх - ≈ 2%, тому не робиться.
- **Одиниці:** CPU ноди - % від усіх ядер; CPU проєкту/процесу - % одного ядра.
- **Температура:** `sensors_temperatures`: `k10temp` (Tctl/Tdie) → `coretemp` (Package id 0) → `cpu_thermal`/`soc_thermal` → `null`; `load_temp_sensor` перекриває. Mac без sudo - `null`.
- **HTTP (лише читання):** `GET /api/load`, `/api/load/series?period=1h|24h|30d`, `/api/load/projects?minutes=1..60`; 503 `{enabled:false}`, коли семплер вимкнено чи нема psutil; `status().global.load` = `{enabled, interval_s, sampler_cpu_pct, last_ts}`. «Проєкти за CPU» беруться з кільця в пам'яті (БД відстає до хвилини).
- Відкинуто: семплінг у тіку демона (дрейф, тік важкий); запис кожні 5 с у `index.db`; `cwd` для всіх процесів щоразу.
- `load.db` лежить у `~/MyVector`, але `relocate` не переписує його `project_path` (шляхи проєктів інші на новій машині); E6-08 вивантажує з `host` і шляхи нормалізує сам. `project_path = ''` - «інше» (і в сирих, і в хвилинних). `load_sample_s` має нижню межу 1 с.

## ADR-013 Витрати токенів: інкрементальний збір із транскриптів в окрему `tokens.db`

2026-11-09, planner E7-01.

- **Джерело** — транскрипти Claude Code `<claude>/projects/<proj>/<session>.jsonl` і `…/<session>/subagents/**/agent-<id>.jsonl` (+ `agent-<id>.meta.json`). Корінь — config `claude_projects_dir`; порожньо = `<claude>/projects`, де `<claude>`: `MYVEC_CLAUDE_DIR` > `CLAUDE_CONFIG_DIR` > `~/.claude` (тести ставлять `MYVEC_CLAUDE_DIR` і знімають `CLAUDE_CONFIG_DIR`). Беруться лише записи `type=assistant` з `message.usage` (рядки без `"usage"` не парсяться — префільтр за байтами). Замір 2026-11-09 на devbox: 8,7 ГБ, 4320 файлів, 365 тис. записів з usage, 195 тис. унікальних, повний прохід ≈ 17 с.
- **Дедуп за `(message.id, requestId)`** глобально (PK): Claude Code пише один запит кількома записами (по блоку контенту) з однаковим usage; форк/resume копіює історію в інший файл (знайдено 4 перетини). Записи `model = "<synthetic>"` і з нульовим usage пропускаються. Usage — верхнього рівня (`iterations` не сумуються).
- **Окрема БД `MYVEC_HOME/tokens.db`**, не `index.db`: транскрипти Claude Code видаляє через `cleanupPeriodDays` (30 днів), тож `tokens.db` і є історією витрат: вона НЕ відновлюється (`rebuild`/перескан не поверне видалені транскрипти) і не повинна жити в «одноразовому» `index.db` (`rebuild`, видалення індексу); запис не конкурує з sync за `db_lock`; та сама модель, що `load.db` (ADR-012). Файл `0600` (разом з `-wal`/`-shm`), власний `schema_version` у її `meta`; `relocate` переписує `cwd` і в ній. Відкинуто: `index.db` v8 (перетин зі схемою E6-01, історія губиться разом з індексом).
- **Інкрементально за зсувом:** `token_files` тримає на файл `(dev, ino, offset, size, mtime)`; читається від `offset` до останнього `\n` (неповний хвіст — наступного разу); інший inode або `size < offset` → з нуля (дедуп не дублює); зниклий файл → `gone=1`, рядки лишаються. Рядки й новий `offset` пишуться однією транзакцією. Один сканер за раз — `state/tokens.lock` (non-blocking).
- **Без тексту:** зберігаються лише ts, моделі (фактична `message.model`, запитана `requestedModel`), `effort`, `cwd`, `gitBranch`, чотири лічильники токенів (+ `cache_write_1h`), session/agent id, `agentType` і `model`/`effort` з meta. `description` агента не зберігається — лише id тікетів, витягнуті regex `\b[A-Z][A-Za-z0-9]*-\d{2,}\b` (до 3; `ADR-…` ігноруються, `E<n>-<nn>` першими). Тест із «сентинел»-текстом у контенті/description/промпті перевіряє байти БД.
- **Атрибуція при читанні** (як ADR-009): проєкт — `project_of(cwd, main_root_of(cwd))`; тікет — пріоритет: id з description субагента (якщо існує в тікетах проєкту) > claim сесії > гілка запису `t/<id>` > сегмент `.worktrees/<id>` у cwd. Гілка береться з кожного запису, не з рядка `sessions`. Головна сесія — агент `main`; її витрати без тікета показуються рядком «оркестратор / без тікета» (субагенти без тікета — «без тікета»), за часом не розносяться. Витрати оркестратора, зроблені, поки його cwd у worktree тікета (`.worktrees/<id>`), належать цьому тікету; у виводі й рядку підсумку агент `main` показується як «оркестратор» (у даних/JSON лишається `main`).
- **Планування:** демон раз на `tokens_scan_s` (60 с) запускає скан в окремому однопотоковому виконавці (тік не блокується, наступний не стартує, поки йде попередній), бюджет `tokens_scan_budget_mb` (512) за прохід; первинний імпорт розтягується на кілька проходів. Без демона `myvec tokens` сканує сам (`--no-scan` вимикає).

## ADR-014 Відповідь на AskUserQuestion з вебу через `cm answer`

2026-11-09, planner E2-06. Доповнює ADR-010.

- **Окрема команда `cm answer <id> (--option N | --text -) [--expect-label L]`**, не прапор `cm send`: `send` лишається «вставити й Enter» з відмовою 4 на будь-якому діалозі (AUQ теж), `answer` працює лише з віджетом AskUserQuestion. Класифікація екрана — чиста функція: AUQ = `Type something.` + `Chat about this` + `Enter to select` + `↑/↓ to navigate`; будь-який маркер permission/startup-діалогу перемагає (→ 4, жодної клавіші). Загальне `Esc to cancel` для розпізнавання не використовується.
- **Стрілки з перевіркою, не цифри:** дельта від `❯`, `Up`/`Down`, повторний capture, Enter лише коли `❯` на цілі (для тексту — коли текст видно в полі). Після Enter віджет має зникнути за 5 с, інакше 1. Відкинуто цифрові клавіші: невідомо, чи цифра одразу підтверджує, і тоді нема кроку перевірки.
- **v1 — одне питання з одиночним вибором, текст в один рядок.** Мульти-питання й multiSelect → 4 (відповідь у терміналі). `--expect-label` захищає від застарілого питання (myvec передає лейбл, якщо він без маски).
- **myvec:** хук `ask` зберігає замасковані лейбли варіантів (лише для одного питання) у `sessions.question_options`; `sessionact.answer_kind` вмикає режим `auq` лише для живої керованої сесії (`mode = send`) і коли cm має `answer` (feature-detect); інакше поведінка ADR-010. POST `/api/sessions/{sid}/resume` приймає `{text}` або `{option}`; текст іде через stdin, у `bus` лише довжина й номер варіанта.

## ADR-017 Пасивне виявлення прогонів тестів

2026-11-10, planner E6-03.

- **Слухач семплера, не новий потік.** `passive.Detector` підключається `Sampler.add_listener` у `nodeload.Runner` (вмикається разом із семплером, `daemon.py` не змінюється). `cmdline` читається лише для busy-процесів з іменем-кандидатом (python*, php*, node, npm, pnpm, npx, uv, pytest, phpunit, vitest, jest), раз на `(pid, create_time)` з негативним кешем; процес, чий батько вже член прогону, приєднується без читання cmdline. Прохід угору за `ppid` (≤ 8) - лише для нового кандидата: корінь - найвищий предок, що теж класифікується (`npm test` над `node vitest`). Відкинуто: cmdline усіх busy-процесів (бюджет < 1 %, ADR-012), окремий потік із `process_iter(cmdline)`.
- **Дедуп з `myvec measure`:** обгортка ставить дитині env `MYVEC_MEASURE_RUN=<run_uid>`; детектор ігнорує кандидата, якщо цей ключ є в env кандидата чи кореня або серед предків є `myvec measure` (старі обгортки, `AccessDenied` на env). З env читаються лише `MYVEC_MEASURE_RUN` і `CLAUDE_CODE_SESSION_ID`, решта ніде не зберігається. Відкинуто: звірка з `pid` рядків `wrapper` у БД (потік семплера мав би читати `index.db`, гонка на старті).
- **Запис лише через журнал** `state/test_runs.jsonl` (події `running` і `done`), фолдить демон щотіку; потік семплера не відкриває `index.db`. `run_uid = passive-<host>-<pid>-<create_time ms>`, `started_at` = `create_time` кореня: перезапуск демона не дублює прогін; зниклий без демона корінь → `lost` (наявний `fold`). Атрибуція гілки/тікета - у `fold` при першій вставці, далі фіксована (ADR-011).
- **Що пишемо:** `source='passive'`, `label` = вид (`pytest`, `artisan test`, `npm test`, ...), `command` маскується `safe_command` (і вдруге на виході, ADR-015); CPU - сума кумулятивних `cpu_time` членів (включно з часом до виявлення), `peak_cores` - пік суми за знімок; RSS, код виходу й сигнал - NULL. `outcome` такого рядка - `ended` («завершено»), не `passed`. Схема v7 без змін.
- **Реалізація:** npm перейменовує процес (`npm test`, argv з порожніми токенами) - `passive._normalize` розбиває такий заголовок; журнал `test_runs.jsonl` пишеться під `flock` (`test_runs.jsonl.lock`: писарі `LOCK_SH`, rename складача `LOCK_EX`), бо писар тепер потік семплера; додані `yarn test`, `bun test`, `paratest`; медіани `summary` лише для `exit_code=0`.
- **Обмеження:** прогін коротший за ~1 інтервал семплера (5 с) може не потрапити; cwd поза зареєстрованими проєктами не записується; watch-режими (`--watch`, `--watchAll`, `vitest watch|dev`) ігноруються.

## ADR-018 Тривога CPU і регресії прогонів обчислюються при читанні

2026-11-10, planner E6-06. Доповнює ADR-003, ADR-012, ADR-015, ADR-017.

- **Тривога CPU - з кільця знімків семплера, без нового потоку й без схеми.** Чиста функція `nodeload.cpu_alert(snaps, pct, minutes, interval)` проходить кільце (720 знімків, 1 год) від найновішого: серія знімків з `cpu_pct ≥ pct`, провали нижче порога до `max(ALERT_GRACE_S, interval)` (15 с) її не рвуть, розрив часу > 3 інтервалів (сон) рве. Тривога активна, коли серія триває до останнього свіжого знімка й довша за `minutes`. Винуватець - `top_projects(ring, onset)`: проєкт, найважчий процес (`top_name`, `top_pid`), середні ядра. Віддається в `/api/load` (`alert`) і в `/api/status` (`global.load.alert`); банер показує лише сторінка «Навантаження» (рішення оркестратора, як у макеті v3), не всі сторінки. Командний рядок не читаємо: якщо в проєкті винуватця є прогін `running` цього хоста, демон додає його поля (`command`, `ticket_id`, `agent`, уже замасковані `testruns._shape`). Після перезапуску демона тривога відновлюється не раніше ніж за `minutes` - прийнятно. Процеси не вбиваються. Відкинуто: окремий потік-сторож (бюджет < 1 %, ADR-012), читання `node_samples` з `load.db` на кожен запит.
- **Регресія - при читанні в `testruns`, не колонка.** `regression` = `null` або `{wall_pct, cpu_pct, median_wall_s, median_cpu_s, n}` (`*_pct` - перевищення медіани у %, `null` для метрики без перевищення). Прогін - регресія, якщо `wall_s` або `cpu_s` більше медіани на ≥ `test_regression_pct` (25 %) серед останніх `test_regression_runs` (10) базових прогонів того самого ключа, що почалися раніше; приріст мусить бути і ≥ `test_regression_min_abs_s` (2 с) в абсолютних секундах (коротка команда 2 с -> 2,6 с не регресія); база з < `test_regression_min_runs` (3) прогонів - регресії немає. Відкинуто: колонка в `test_runs` (схема v8 і міграція двох розгорнутих індексів, застаріває при зміні порогів).
- **Ключ і база не змішують джерела.** Ключ = `(project_path, source, label)` для `wrapper` з `--label`, інакше `(project_path, source, command)`. Для пасивних - `command`, не `label`: `label` там лише вид (`pytest`), і прогін одного файлу змішався б із повним набором. Базові прогони: `wrapper` - лише `passed`; `passive` - `ended` (коду виходу немає, інших успішних не буває). `failed`, `interrupted`, `lost`, `running` у базу не входять і самі регресією не позначаються (UI показує «впали» замість «регресія»). Прогін `running` позначається наживо лише за wall: `now − started_at` проти медіани.
- **Пороги в `config.toml`:** `load_alert_pct` (85), `load_alert_minutes` (5, ≤ 55 і ≤ `720·load_sample_s/60 − 1`: кільце 720 знімків, при малому `load_sample_s` довша межа ніколи б не спрацювала), `test_regression_pct` (25), `test_regression_runs` (10), `test_regression_min_runs` (3), `test_regression_min_abs_s` (2). UI бере поріг з `/api/load` і правило регресії з `/api/tests/runs` (`regression_rule`), не хардкодить 85/25.

## ADR-019 Inbox правок з UI: файл у теці тікетів, читання теки напряму

## ADR-020 Здоров'я тікетів: окрема severity `health`, обчислення при читанні

2026-11-10, planner E3-03. Доповнює ADR-002, ADR-005, ADR-008, ADR-009; підхід як ADR-018.

- **Структурні проблеми лишаються помилками `check`.** Висячі `parent`/`deps`/`blocks`, несиметричні зв'язки й цикли deps/parent уже є (`dangling_*`, `asym_*`, `dep_cycle`, `parent_cycle`, severity `error`); E3-03 їх не дублює, лише показує в UI так само, як поради.
- **Поради здоров'я - нова severity `health`** (поряд з `error`/`warning`): `too_big` (розмір L), `no_ac` (нема жодного чекбокса Acceptance criteria), `stale` (давно не оновлювався), `no_session` (🟦 без активної сесії), `blocked_ready` (⛔, а всі deps уже ✅: можна розблокувати), `dep_cancelled` (deps містить 🚫). Разом шість правил; пороги `stale`: ⬜ 30, 🟦/🟨 7 днів. Ніколи не валять `check --strict` і не блокують `index`: поради не є порушенням канону, а `stale` залежить від дати й ламав би CI/хуки щодня. CLI друкує їх тегом `HEALTH` і рахує окремо. Відкинуто: `warning` з винятками для окремих кодів у `--strict` (неочевидно, `too_big` на справжньому L-тікеті E4-02 одразу зламав би `scripts/tickets.py check`).
- **Рахуються лише для листів у роботі.** Групи (`kind: group`) і статуси `done`/`cancelled`/`frozen` порад не мають (перевіряються статуси todo, in_progress, review, waiting, blocked, partial) (інакше 🟦-групи E1/E6 і закриті тікети засипали б дерево).
- **Обчислення при читанні, не в `ticket_issues`.** Чиста `tickets.health(nodes, today, sessions=None, now=None)` над мапами з полями `id, kind, status, size, ac_total, updated, path` (і `Ticket`, і вузол `ticket_tree`). `ticket_issues` оновлюється лише при зміні відбитка теки (ADR-005), тож `stale` у таблиці застарів би; схема не міняється (як ADR-018). `ticketdb.project_tickets`/`get_ticket` дописують поради в `issues`, `projects_summary` додає їхні тікети в `n_problems` (об'єднання множин id, без подвійного рахунку).
- **Пороги - константи в `tickets.py`**, не конфіг: `STALE_DAYS = {"in_progress": 7, "review": 7, "todo": 30}`, `NO_SESSION_GRACE_DAYS = 1`. Без `updated` або з невалідною датою `stale` не рахується.
- **`no_session` лише локально й лише в UI/API.** Сесії - з `sessions.by_ticket` цієї ноди (ADR-009); активна = будь-який `effective_state`, крім `ended`. Порада, якщо активної немає і від останньої активності (`max(updated, last_seen прив'язаних сесій)`) минуло ≥ 1 доби (оркестратор ставить 🟦 трохи раніше, ніж стартує coder). CLI `check` без БД її не рахує. Хмара (E4) отримує поради кожної ноди готовими в payload; `tracker.js` лише показує `issues`.
- **Наслідки.** `tickets.health` не знає БД; `ticketdb` додає `n_health` до `projects_summary` (UI його не показує, `n_problems` - об'єднання id). Грація `no_session` рахується календарними днями (`updated`/`last_seen`), `now` лише для ознаки активності сесій. У картці порадам відповідає `<ul class="health">` (`tracker.js`), у дереві - `warn-ic` з `title`, фільтр «Проблеми» враховує їх.

## ADR-022 Сповіщення про inbox: у наявних хуках, лише основний checkout, без тексту

2026-11-10, planner E3-02. Доповнює ADR-007, ADR-019.

- **Вбудовано в наявні команди хуків.** `hook session-start` (SessionStart) і `hook session-event` для `UserPromptSubmit` друкують рядок `[myvec] inbox: N new in <dir> (<id> <kind>[->status], ...)`; stdout цих подій Claude Code кладе в контекст. `settings.json` і `hooks.install()` не змінюються, тож `myvec install-hooks` перезапускати не треба (лише перевстановити пакет). Відкинуто окремий хук `hook inbox-notify`: ще один процес на кожен промпт і ручний `install-hooks` на обох машинах.

Події з `agent_id` пропускаються. Дочірні cm-сесії в основному checkout рядок бачать (даних хука, щоб їх відрізнити, нема); обробляє лише оркестратор за каноном.
- **Без тексту коментаря.** У контекст іде лише id, вид і `requested_status` з `tickets.STATUS_KEYS`: текст з UI не стає інструкцією в промпті, оркестратор читає файл сам.
- **Антиспам - стан на сесію.** `MYVEC_HOME/state/inbox_seen/<session_id>` (відсортовані імена файлів, `os.replace`). SessionStart показує завжди, коли inbox не порожній; UserPromptSubmit - лише коли з'явились імена, яких не було; SessionEnd стан видаляє, файли старші 7 днів прибирає SessionStart. Відкинуто стан на проєкт: друга сесія оркестратора не дізналася б.
- **Бюджет:** stdlib, ліниві імпорти `projects`/`inbox`/`tickets` лише в проєкті з маркером; будь-яка помилка - тиша й exit 0 (ADR-007). Команди `myvec ticket inbox` поки нема: регламенту в каноні досить.

## ADR-023 Старт у теці з кодом: факти в `myvec scaffold --detect`, пофайлове злиття, транзакційний запис

2026-11-10, planner E5-06. Доповнює ADR-021.

- **Факти - CLI, рішення - skill.** `myvec scaffold --detect [--root] --json` детерміновано визначає стек, менеджер пакетів, команди тестів/лінтера, ознаки UI, маркер, наявний процес, формат тікетів (`none|canon|foreign`), стан git і мову наявних документів; нічого не пише й не питає. Неоднозначне (монорепо, URL UI, опис) не вгадується - іде в `unknown`, skill питає лише його. Відкинуто: детекцію самим Claude (не тестується) і окрему команду `myvec detect` (один генератор, ADR-021).
- **Читання за білим списком** імен файлів (маніфести, lock-файли - лише наявність, README/CLAUDE.md/`docs/*.md` для мови), ліміт 256 КБ, жоден компонент шляху не симлінк (`detect._plain`; симлінк-тека `.claude`/`docs`/`docs/todo` не читається), без мережі й запуску інструментів проєкту; `filters.is_denied_path` - додатковий бар'єр (не покриває, напр., `.dev.vars`, тому білий список головний). Значення з hard secret у чернетку не потрапляє.
- **Пофайлове розв'язання конфліктів:** `--keep PATH` (лишити своє), `--overwrite PATH` (шаблон, `.bak-<ts>`), `--append CLAUDE.md` (дописати розділ процесу в кінець, `.bak-<ts>`; якщо розділ уже є - помилка, злиття вручну). Без явного прапорця конфлікт блокує весь запис, як і раніше. `--diff` показує unified diff з `filters.mask_secrets`; файл із hard secret - без diff.
- **Чужі тікети не мігруються:** при `tickets: foreign` шляхи `docs/todo/**` - `skip-foreign`, індекс не перегенеровується; міграція - `myvec ticket migrate` (E5-01).
- **Транзакційний apply:** план несе відбиток (`sha256`) кожного цільового шляху; apply спершу звіряє всі відбитки й `_safe` (розбіжність - код 3, нічого не записано), потім пише всі tmp (`O_EXCL|O_NOFOLLOW`), потім заміняє (`create` - `os.link`, без перезапису файла, що з'явився); помилка в фазі заміни - відкат з `.bak` (best-effort, не атомарно для ФС у цілому); `.bak` видаляється лише для успішно відновлених файлів, невдалі перелічуються в помилці (код 2) зі шляхом до `.bak`. **Межа гарантії:** відбитки живуть лише в межах одного процесу (plan і apply в одному запуску); зміна між окремим `--dry-run` і запуском не виявляється, правка під `--overwrite` лишається лише в `.bak-<ts>`. Коди: 0 ок, 2 помилка вводу/відповідей/нерозв'язаний конфлікт, 3 тека змінилась між планом і записом (у т.ч. симлінк чи файл, що з'явився). `--keep` на `merge` (settings, `.gitignore`) лишає файл; `--no-tickets` пропускає `docs/todo/**`.
- **Git:** коміт лише шляхів з `--json` (create/merge/overwrite/append) через pathspec (`git commit -- <paths>`), застейджені чужі зміни не потрапляють; шляхи scaffold, що були брудні до запуску, у коміт не йдуть. Наявний маркер - `myvec init` не кличеться.
- **Мова:** документи процесу (агенти, rules) - англійські шаблони; для наявного проєкту виявлена мова пропонується в інтерв'ю й іде лише в слот `docs_language`, рішення власника для нових проєктів - слот. Для наявного проєкту (рішення власника 2026-11-10): агенти/rules/CLAUDE.md - англійською, мова тікетів - мова проєкту (виявлена, підтверджується питанням, рекомендована - вона).
- **Уточнення E5-07.** `--keep` діє й на рядок `create` (файл не створюється). Для наявного проєкту (`foreign` або `--no-tickets`) перша група не планується (`render(with_group=False)`), `first_group` не питають.

## ADR-024 Міграція тікетів: CLI лише виявляє, брифує й перевіряє; переписує агент проєкту

2026-11-10, planner E5-01. Доповнює ADR-001, ADR-002, ADR-004.

- **Поділ.** `myvec ticket migrate` детермінований і за замовчуванням лише читає: `--detect` (кандидати й статистика формату, `--json` - контракт для E5-06; додатково `n_items`, `n_boxes`, `legacy_epic`, `legacy_groups`, `git_root` відносно кореня проєкту), `--brief [--out FILE]` (markdown-бриф для агента проєкту з мапою полів/статусів), `--check` (що лишилось до канону, exit 0 лише коли все). `--dir` вибирає теку, коли кандидатів кілька (без нього неоднозначність - код 2 з переліком). Семантичні рішення (розбиття `todo.md`, схема id, невідомі статуси) приймає агент проєкту з власником за брифом. Відкинуто повний автоконвертер: формати пілотів різні (майже канон / один todo.md / шапки без id), помилка тихо зіпсувала б сотні файлів і історію.
- **Виняток - `--fix`:** лише механічні безвтратні правки шапки (`epic` -> `parent`, `id`/`kind: group`/`status` для синтетичних груп `index.md`; порожній `id:` заповнюється на місці, без дубля ключа; `index.md` з `kind: ticket` пропускається), dry-run за замовчуванням, запис - лише `--write`, ідемпотентно (один прохід), тіло не чіпається. Знімає перехідну підтримку ADR-002 у мігрованих проєктах.
- **Безпечність запису.** `--dir` має лежати всередині `--root` (`ticketmigrate.inside()`: `resolve()` під root і жоден компонент шляху не симлінк; інакше код 2); те саме перевіряють `fix_plan` (тека й кожен файл, симлінки пропускаються) і `apply_fixes` (усі шляхи до першого запису). Перед записом файл перечитується й звіряється з текстом, з якого будувався план; змінений - відмова.
- **Звіт без вмісту.** Detect і бриф беруть лише ключі шапки, значення статусів і заголовки розділів (усе через `mask_secrets`, hard secret - відкидається), не тіло тікетів.
- **Історія.** Одна гілка й один PR у проєкті; окремий коміт лише з `git mv`, потім правки; Log не переписується, рядок міграції - один, у тікеті міграції проєкту. `todo.md` після розбиття лишається коротким файлом-посиланням на нову теку (`leftover_todo` у `--check`).
- **Статуси й мова.** Форма статусів проєкту зберігається (емодзі чи ключі); без статусів - ключі. Мова тікетів (розділи, тексти, INDEX) - мова проєкту. Парсер знає російську ціль `## За один заход` (`tickets._GOAL_HEAD`), а `ticketops.lang_for` повертає `ru` за цим заголовком у `ticket-template` і дає `INDEX.md` російськими заголовками (`_L["ru"]`). Агенти, rules і CLAUDE.md - англійською (рішення власника). Відомо: `blocked_by: —` у брифі мапиться в `deps` без примітки, що `—` означає `[]` - агент проєкту має це знати.
- **Уточнення E5-07 (пілот project-a).** `--detect`/`--check` попереджають `legacy_script`: скрипти проєкту (`package.json`, Makefile, `scripts/*`), що згадують `tickets` (і старі поля `epic`/`estimate`) - лише `файл:рядок`, без вмісту, файли з deny-list `filters.py` (`.env*`, ключі) не читаються; код виходу `--check` не міняється, `--detect --json` пише попередження в stderr. `--fix` ставить статус створеної групи за дітьми (усі ✅ - ✅ з найпізнішою датою, є 🟦/🟨 - 🟦, інакше ⬜; для ключів done/in_progress/todo), наявний статус групи не чіпає. INDEX: загальний прогрес `N% (k/n)` у всіх мовах - відсоток зважений (враховує часткову роботу), лічильник `k/n` лише завершені листи, тож «75% (0/1)» не розбіжність. Вивід `ticket check`/`index`/`migrate --check` мовою тікетів проєкту (`lang_for`: uk/ru/en).
- **Уточнення E5-08 (пілоти project-b, project-c.lv).** (1) `migrate --split` для формату «один файл» (`single_file`): dry-run за замовчуванням, `--write` пише; параметри `--dir FILE --group-id --group-slug --group-title --dest --status-style`. Текст переноситься дослівно (заголовок пункту стає H1, решта - у `index.md` групи), перевірка «жодного рядка не втрачено», джерело перечитується перед записом; старий файл стає посиланням з маркером, що виключає його з кандидатів, повторний запуск - no-op (код 0, «already split»). (2) `--fix` призначає `id` шапкам без нього: числовий префікс імені файла (`E1-05`), інакше ім'я файла (`01-home`); `<група>-NN` лише при колізії (тоді `ticket check` дасть `id_filename_mismatch` і файл перейменовує людина); файли з префіксом обробляються першими. Нові ключі вставляються лише на межі ключів (`_value_end`): багаторядкові значення (простий скаляр з відступом, лапки, `[...]`, `|`-блок) не розрізаються, `set_fm_line` на них відмовляє. Статус групи з `partial`-дитиною - in_progress. (3) `--add-goal-heading` - єдиний шлях, яким міграція змінює тіла (вставляє заголовок цілі); `no_goal` тоді не лишається в `leftover`. (4) Парсер знає російські/українські заголовки AC; `lang_for` без шаблона бере мову із заголовків `## ` тікетів (ru-маркери: «задачи», «сделано» тощо; «контекст» спільний для uk і ru, не сигнал), легенда статусів INDEX локалізована. (5) `ticket index --index-name NAME` і відмова (код 2) при збігу імені без урахування регістру (`INDEX.md` vs чужий `index.md` на macOS). Ім'я **не зберігається**: `ticket index` без прапорця на такій теці знову відмовить; обхід - `tickets_index_cmd` зі слотом `--index-name`. `migrate --check` не рахує кандидатом файл без шапки з маркером `generated:start`.

2026-11-10, planner E0-05. Доповнює ADR-021.

- **Три шари.** (1) Skill `/myvector` (`orchestrator.md`) - загальна політика оркестратора для всіх проєктів з `.claude/agents` (бриф 4 рядки, звіт агента ≤ 40 слів «status · tests · blockers», не читати великі артефакти й серії скріншотів, тихі команди, статус власнику лише на рішеннях, передача при ~200 тис. контексту). (2) Шаблони scaffold (`partials/general-rules.md`, `.claude/rules/workflow.md`) - процес проєкту, рендер за ADR-021: тут лише ліміт звіту і короткий розділ «Orchestrator context» з посиланням на skill. ## ADR-026 Дочірня сесія на тікет: оркестратор бачить лише рядок статусу

2026-11-10, planner E0-06. Доповнює ADR-010, ADR-025.

- **Рішення.** Конвеєр тікета (planner → coder → tester → reviewer → docs-writer) веде дочірня сесія у worktree `.worktrees/<ID>`; оркестратор не тримає в контексті брифи й звіти агентів, а отримує один рядок статусу на точку зупинки. Політика - у skill (`orchestrator.md`, розділ «Child session per ticket»).
- **Механізм (рішення власника):** обидва - `start_session` + `SendMessage` де інструмент є, інакше (і для відновлення) `cm` (ADR-010: текст лише stdin, `busy`/код 4 не обходити). Параметри `start_session` у skill не описуються, доки не перевірені на машині (урок E5-06).
- **Ролі.** Дочірня: агенти `.claude/agents/*` (effort ≤ medium, без Fable), цикл reviewer → coder до 0 Critical/Important, коміти в `t/<ID>-<slug>`, затвердження плану й UI-дизайну власником сама через `AskUserQuestion`. Не міняє `status`, не пушить, не відкриває PR, не зливає, не перевстановлює `myvec`, не стартує інших дочірніх. Оркестратор: worktree, статус, push, PR (рішення власника), squash-merge, видалення worktree, перевірка фактами, вартість, слот qa (один демон - паралельних qa немає).
- **Точки зупинки:** план готовий (`wait-owner`), UI-дизайн, готово до PR, блокер, потрібен qa, контекст дочірньої ~200 тис. (handoff у `## Log`).
- **Рядок статусу (≤ 40 слів):** `<ID> · <етап: plan|code|test|review|docs|qa|ready> · <ok|wait-owner|wait-qa|blocked> · tests <N passed | fail N | -> · <PR-ready|-> · blockers: <… | none>`. Деталі - лише в `## Log`; транскрипт і `cm logs` дочірньої оркестратор не читає (крім хвоста ≤ 30 рядків при блокері).
- **≤ 2 лінії:** лінія = дочірня сесія = worktree; перед стартом `git worktree list` і тікети 🟦/🟨; третю не стартувати. Тримається дисципліною, не кодом.
- **Наслідки.** Інші проєкти отримують політику через `install.sh`; їхні `workflow.md` - після E0-07. Відкинуто: саб-агент `Agent` на весь конвеєр (не викликає інших агентів, немає `AskUserQuestion`, звіт усе одно в контексті оркестратора); лише `cm` з опитуванням (більше контексту й затримок, ризик Enter у permission prompt).

## ADR-027 Зворотний канал уроків: `myvec ticket lesson` поверх `inbox.write`, вирішує оркестратор vector-local

2026-11-10, E0-08 (прийнято, реалізовано). Доповнює ADR-019, ADR-022, ADR-025 (шар 3).

- **Рішення.** Оркестратор іншого проєкту пропонує загальний урок командою `myvec ticket lesson --title T [--to NAME] [--from NAME] -` (текст лише зі stdin). Команда пише в inbox цільового проєкту (дефолт `lessons_project = "vector-local"`) лише через `inbox.write`; корінь - `projects.root` з БД (read-only), тека тікетів - з маркера. Відкинуто: POST у API демона (потрібен наявний id тікета, CSRF, живий демон) і прямий запис файла (обхід захищеного запису ADR-019).

- **Вміст.** Крім наявних правил (hard secret - відмова, літерали маскуються, ≤ 4000 символів, без керівних) урок із абсолютним домашнім шляхом або шляхом у `MyVector/vault/` відхиляється (`private`, код 2; перевірка нечутлива до регістру, ловить `~`/`$HOME`/`${HOME}` і `\\`): урок - узагальнене правило без даних машини. `filters.py` не змінюється. Stdin обмежено `MAX_TEXT*4+1`.
- **Обробка.** Хук (ADR-022) показує лише `lesson<-<from>` і вказівку на skill; хвіст рахується по всіх елементах черги, при нестачі місця скорочується список частин (`+N`), не хвіст. Оркестратор vector-local в основному checkout вирішує: політика оркестратора -> `orchestrator.md`, процес проєктів -> шаблон scaffold (ADR-021), лише для vector-local -> `docs/lessons.md`, інакше відхилити; рішення - у коміті, файл видаляється. Агенти й дочірні сесії не пропонують і не обробляють.
- **Наслідки.** Inbox локальний для машини (git його не бачить): урок із devbox обробляється на devbox. Схема БД не змінюється.

## ADR-028 Версія процесу й стан scaffold у проєкті: копія рендеру як база 3-way

2026-11-10, E0-07 (прийнято, реалізовано). Доповнює ADR-021, ADR-023, ADR-025.

- **Версія.** Ціле `PROCESS_VERSION` у `src/myvec/scaffold/__init__.py` (одне джерело, їде у wheel), стартує з `1`. Підіймається на кожну зміну рендеру: тест-сторож звіряє `render_digest` (sha256 рендеру + злитий `.gitignore` + `settings_allow`) двох фікстур (vector-local і `minimal.answers.json`) із `tests/fixtures/scaffold/process_version.json`; зміна шаблону чи дефолту слота без підняття версії - червоний тест.
- **Стан.** Один файл `.myvec/scaffold.json` у корені проєкту (комітиться в git проєкту): `{"format": 1, "version": N, "answers": {...}, "files": {rel: {"mode": "owned|keep|append", "sha256", "base"}}}`; `sort_keys`, `indent=2`, без часових міток - повторний запуск дає ті самі байти (`same`, `.bak` нема). `mode`: `owned` (на диску рендер), `keep` (власник лишив своє), `append` (CLAUDE.md з дописаним). `skip`/`skip-foreign` у стан не йдуть; `.gitignore` і `settings.json` без бази (зливаються ідемпотентно). `sha256` - від нормованого тексту рендеру.
- **Насінна група поза станом.** `docs/todo/<id>-<slug>/index.md`, яку scaffold створює лише в порожньому проєкті, у `files` не потрапляє: при повторному запуску `with_group` стає false (тека вже є), і стан інакше змінювався б побайтово. Цим файлом E0-09 не керує.
- **База 3-way - копія рендеру, не хеші.** Відкинуто: хеші + повторний рендер старою версією (старих шаблонів у wheel нема, а тягти всі версії чи брати з git vector-local крихко); база з git-коміту проєкту (scaffold не комітить, коміт може містити правки власника). Ціна - десятки КБ JSON у репо проєкту.
- **Місце - `.myvec/`, не `.claude/`:** `.claude/` належить Claude Code (`.claude/agents/*.md` вантажаться як агенти), чужий файл там ризикує колізіями. `.myvec/` прихована, не індексується.
- **Запис** - ще один (останній) рядок плану (`create`/`same`/`merge`), у тій самій транзакції `apply` (ADR-023: відбиток, `.bak-<ts>`, відкат); у `--dry-run` показується, але не пишеться; при нерозв'язаному конфлікті не пишеться. `STATE` у `--overwrite/--keep/--append` - помилка (код 2); `--dry-run --diff` текст стану не друкує. Hard secret у тексті стану - код 2.
- **Читання** - `scaffold.state.read(root)` ніколи не кидає (у т.ч. `RecursionError` на глибокому JSON): `status` = `none` (файлу нема - «невідома версія», не помилка) | `current` | `outdated` | `newer` | `invalid` (симлінк, > 1 МБ, не JSON-об'єкт, `format`/`version` не ціле ≥ 1). CLI `myvec scaffold --state [--root] [--json]`, exit 0; вивід без answers і баз; невідомий `mode` відкидається.
- **Наслідки.** Проєкти, розгорнуті до E0-07 (project-a, project-b, project-c.lv), мають `status: none`; стан їм створює E0-09 (повторний `scaffold` з відновленими answers, `mode: keep` для відмінних файлів). vector-local стану не має: його процес звіряє еталон-тест (ADR-021).

## ADR-029 Лог пошуків без тексту і метрика myvec проти grep з транскриптів

2026-11-11, E8-02 (прийнято, реалізовано; UI-картка й `GET /api/search/usage` - окремо в E8-06). Доповнює ADR-013 (білий список `tokens.db`: + `tool_calls`).

- **Текст запиту не зберігається** в `logs/searches.jsonl`: лише `q_len`, `q_words`, `q_ident`, `q_secret` і `q_hash` = HMAC-SHA256 з локальною сіллю `state/searchlog.salt` (`0600`), перші 16 hex; при hard secret хеш `null`. Сіль не дає перебрати короткі запити словником; хеш потрібен лише для повторів. Порожній чи короткий файл солі (збій між створенням і записом) видаляється й генерується наново, у крайньому разі - випадкова сіль на процес, ніколи не нулі. Відкинуто: маскований текст (маска ловить лише відомі формати секретів, а запити агентів містять назви клієнтів, шляхи, фрагменти коду - зайве для метрики).
- **Шина й `queries.jsonl`** лишають текст для «Останніх пошуків» в UI, але `q` маскується (`filters.mask_secrets`, hard secret -> `•••`) до публікації/запису. Раніше обидва писали сирий `q`; старі рядки `events.jsonl`/`queries.jsonl` зі збірок до E8-02 лишаються з сирим `q` до ротації (або чистити вручну).
- **Сесія** - `CLAUDE_CODE_SESSION_ID` клієнта: direct-mode читає сам, демону CLI передає заголовком `X-Myvec-Session` (`daemon_client`); і клієнт, і сервер (`searchlog._session`) пропускають лише UUID-подібне значення (значення з `\n` інакше валило б `http.client`). UI-пошуки - `via=ui`, сесії немає. **Агент** (main/субагент) у середовищі не видно: визначається при читанні з транскриптів (найближчий виклик `myvec` тієї ж сесії в ±5 с), не пишеться.
- **Файл, не таблиця:** jsonl з ротацією 8 МБ × 2. Не `index.db` (похідна, `rebuild` стер би історію), не `tokens.db` (його пише лише сканер під `tokens.lock`; direct-mode CLI конкурував би). Режим `0600` виставляється при створенні й перевіряється після кожного дописування (ротація створює файл заново з umask). Бекапиться разом із `~/MyVector`; `relocate` не потребує правок шляхів у ньому, лише в `tool_calls.cwd`.
- **Метрика «myvec проти grep» - з транскриптів**, не з логу: обидва боки з одного джерела й однаково для субагентів. Токен-колектор тим самим проходом класифікує блоки `tool_use` (`Grep/Glob`; Bash `grep/rg/find/fd/ls -R` як перша команда сегмента, не після `|`, `timeout` пропускає значення `-k/-s`; `myvec search`/`recall`) і пише в `tokens.db.tool_calls` лише `tool_id, file_id, ts, seq, cat, cwd`; команда й вивід не зберігаються. Не класифікується `python -m myvec search`.
- **Міграція `tokens.db` v1 -> v2:** колонка `token_files.tool_seq` і одноразовий дочит наявних транскриптів (`offset` -> 0 лише для `gone=0`), щоб `tool_calls` отримала історію; `token_usage` ідемпотентна за PK, суми не міняються. Перевірка версії - поза транзакцією й повторно під `BEGIN IMMEDIATE` (гонка демон/CLI); readonly-з'єднання міграцію не запускає (на v1 `tool_calls` просто порожня).
- **Промах** = після `myvec search` у тому самому транскрипті в межах 10 викликів був self-пошук. «Попадання через Read» не рахується - потрібен текст видачі.
- **Маршрут у журналі (E8-08):** поле `route` = `vector|hybrid|fts-fallback` - **фактичний** маршрут (`search.effective_route`), а не запитаний: коли ембеддинг недоступний (Ollama впала), запит `vector`/`hybrid` іде лише по FTS і пишеться як `fts-fallback`. Схема журналу не змінена, лише значення; старі записи без `route` рахуються як `?`. `fts-fallback` лишається myvec-пошуком у метриці (рахунок з `tool_calls.cat`, не з `route`). Видача при fallback не змінюється.
- **Агрегат при читанні** (`searchstats.usage`), проєкт - як у витратах (`project_of_cwd`); CLI `myvec searches [--days N] [--project P|.] [--json] [--no-scan]`.
- **Наслідки.** Текст запитів з нового логу не відновити - свідомо. `tokens.db` стає v2: старішу збірку на тій самій БД не запускати.

## ADR-030 Крос-проєктні знання: зведення по проєктах, drill-down, opt-out `shared = false` з маркера

2026-11-11, E8-05 (прийнято, реалізовано). Не змінює ранжування (`bench/REPORT.md`) і схему БД.

- **Зведення - окремий прапорець `--by-project`**, не новий дефолт `--scope all`: наявний вивід, на який спираються агенти, skill і UI, лишається побайтово тим самим. Зведення групує хіти наявного `search.search(scope="all")` за `top_level` проєкту (для `kind=all` окремі проходи code/memory, щоб `max_memory_hits` не з'їв пам'ять), поточна родина - одним рядком. Формула балів, константи й bench не змінюються; порогу «знайдено» немає (лише сортування й ліміт), поріг - тільки через `bench/`.
- **Drill-down `--project X`** = пошук `scope="project"` від ctx кореня X (`ctx.current`), з `share_global=False`, щоб не домішувати global-пам'ять. Нової логіки вибору репо немає.
- **Opt-out читається з `.myvector.toml` під час пошуку** (`shared`, дефолт `true`), з кешем за `mtime`, а не колонкою `projects`. Відкинуто колонку: міграція схеми (конфлікт із паралельними тікетами), правка маркера діяла б лише після sync, а маркер у глобальних git excludes і watcher його може не побачити. Ціна - stat + парсинг кількох маркерів на `scope=all` (мілісекунди).
- **Межі.** Сховано проєкт і нащадків для будь-якого ctx поза його `top_level`-родиною (CLI, демон, UI-пошук, зведення, `--project`); родина бачить себе. Global-пам'ять не зачіпається. Зіпсований TOML або не-bool `shared` -> прихований (fail-closed); відсутній маркер або корінь -> спільний (дефолт власника). Перегляд пам'яті в UI (інструмент власника) фільтр не застосовує (`respect_shared=False`). `filters.py` не змінюється.
- **Сумісність.** Схема БД не змінюється; старий демон без перезапуску ігнорував би нові поля, тож CLI падає в direct mode, якщо у відповіді нема маркера `cross`.

## ADR-032 Вид пошуку `docs`: фільтр шляху до KNN, без схеми і без зміни балів

2026-11-11, E8-03 (реалізовано).

- **`--kind docs`** - четверте значення поряд із `code|memory|all`: підмножина code-чанків із розширенням з `DOC_EXTS` (`.md .markdown .mdx .rst .adoc`), без пам'яті. Документ визначається за розширенням шляху в `branch_files`, не за теками і не за `blobs.lang` (`lang` = `markdown` лише для `.md/.markdown`; шлях - властивість гілки, не блоба). `.txt` не входить (requirements/robots).
- **Фільтр до KNN**, не після: у KNN по партиції `repo_id` додається `rowid IN (<vec_rowid doc-чанків гілки>)` (sqlite-vec 0.1.9 це підтримує), у FTS - предикат шляху в WHERE. Постфільтр top-200 губив би доки в проєктах, де код ближчий. Відкинуто: metadata-колонка `is_doc` у `chunks_vec` (перебудова vec-таблиць на двох розгорнутих індексах; шлях залежить від гілки, а чанк спільний).
- **Ранжування не змінюється:** та сама формула (косинус × пом'якшена вага, RRF/2·61), `kind=all` без підняття доків. Буст доків для питань «чому/що вирішили» і авто-роутинг у `docs` - лише через `bench/`, окремо.
- **Сумісність:** схема БД і `rebuild` не змінюються; демон без перезапуску відхиляє `kind=docs` (CLI друкує `--kind must be code|memory|all`, код 1, у direct mode не падає), тож після оновлення обов'язковий `myvec install-daemon`; це зазначено в README. Допустимі значення - `search.KINDS`, спільні для CLI й демона; `crossproject.summarize` теж приймає `docs`.

## ADR-033 Watcher на Linux: обрізаний обхід через підклас watchdog, ліміт stderr демона truncate-ом

2026-11-11, planner E6-12. Доповнює ADR-017 (фонові потоки демона).

## ADR-035 `myvec scaffold --update`: 3-way через `git merge-file`, база - копія рендеру зі стану, запис лише з `--write`

2026-11-12, E0-09 (реалізовано, `src/myvec/scaffold/update.py`). Доповнює ADR-021, ADR-023, ADR-028.

- **Злиття - `git merge-file -p`** (ours = файл на диску, base = `files[rel].base` з `.myvec/scaffold.json`, theirs = новий рендер). Тимчасові файли - у приватній `mkdtemp` (0700, поза проєктом), видаляються у `finally`; оточення ізольоване від конфігів користувача (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`), глобальний git config не читається й не міняється. Код 0 - чисто, 1..127 - конфлікт (маркери ніколи не пишуться в проєкт), інше - помилка (код 2). Нема `git` - зрозуміла відмова, код 2. Відкинуто: власний diff3 на `difflib` (`SequenceMatcher` з autojunk на файлах > 200 рядків дає інші вирівнювання, ніж Myers; крайні випадки довелось би тестувати самим), пакет `merge3` (нова залежність заради однієї функції; `uv tool install` не читає lock). Сусідні правки git вважає конфліктом - це консервативно й прийнятно.
- **База - копія рендеру зі стану (ADR-028),** не рендер старою версією й не git проєкту. Answers - зі стану; `--answers FILE` дозволено як заміну (зміна слотів під час оновлення). Стан-answers, невалідні для нової версії, - код 2 з порадою передати `--answers`.
- **Дії по файлу** (`mode` зі стану): `owned`/`append` - `same` (нормований диск = новий рендер), `unchanged` (шаблон не змінився, правки проєкту лишаються), `update` (диск = база, перехід на новий рендер), `merge` (чисте 3-way), `conflict`; `keep` - не чіпається (`keep`). Файл зі стану зник із диска - `conflict` (`--overwrite` відновлює, `--keep` лишає видаленим, `mode: keep`). Файл, якого шаблон більше не має, - `orphan`: на диску лишається, зі стану прибирається. Новий файл шаблону поза станом: під `docs/todo/` - `skip` (тікети проєкту), інакше як у плані scaffold (`create`/`same`/`conflict`). Насінна група не рендериться (`with_group=False`). `.gitignore` і `settings.json` зливаються ідемпотентно, як у scaffold. `append`-CLAUDE.md зливається звичайним 3-way: дописані розділи збігаються з базою, власна шапка - правка проєкту.
- **Розв'язання конфлікту:** `--overwrite PATH` (новий рендер, `.bak-<ts>`), `--keep PATH` (лишити диск; `mode` не міняється, база стає новим рендером - «моя версія вже враховує цю зміну шаблону»); ручне злиття = відредагувати файл і запустити з `--keep PATH`. `--append`, `--no-tickets`, `--ticket-template`, `--detect`, `--state`, `--dry-run`, `--diff` разом з `--update` - код 2.
- **Згода - `--write`** (як `ticket migrate --fix --write`, ADR-024): `--update` без неї лише показує план і diff (диск → те, що буде записано; для конфлікту - зміну шаблону база → новий рендер), маскування `filters.mask_secrets`, файл із hard secret - без diff. `--write` без `--update` - код 2.
- **Запис** - наявний транзакційний `apply` (ADR-023: відбитки, `O_EXCL|O_NOFOLLOW`, `os.link` для create, `.bak-<ts>`, відкат) без послаблень; злиті тексти передаються як готові тексти рядків `merge`. Новий стан (`version = PROCESS_VERSION`, бази = новий рендер) - останній рядок тієї ж транзакції; конфлікт - не пишеться нічого. **Знімок:** `update._snap` читає байти файла один раз, і текст для злиття, і відбиток (sha256 тих самих байтів) беруться з нього - правка під час `merge-file` дає `ScaffoldChanged` (код 3), а не втрачається (рев'ю E0-09). **Межа гарантії:** між переглядом і `--write` (два процеси) зміна не виявляється відбитком, але `--write` зливає заново з поточним диском, тож правка не губиться (на відміну від `--overwrite` у bootstrap).
- **Коди:** 0 - перегляд без конфліктів, записано, або вже актуально; 2 - нема стану (`none`: «спершу bootstrap, розділ Existing code»), `invalid`, `newer` («онови myvec»), невалідні answers, нема git, недозволені прапорці, секрет у стані; 3 - нерозв'язані конфлікти (нічого не записано) або тека змінилась між планом і записом.
- **`--json`** - об'єкт `{status: preview|written|conflict|current, from_version, to_version, files: [{path, action, diff | template_diff | diff_withheld}], conflicts: [...], write: [...], backups?: [...]}` (`backups` - лише після запису); `write` - шляхи, що записані (або будуть записані) - лише їх skill комітить pathspec-ом (`.bak-*` ніколи).
- **Самообслуговування (вимога власника 2026-11-11):** skill `/myvector`, розділ «Оновити процес/конвенцію», веде оновлення в самому проєкті без оркестратора vector-local: `--state` → `--update` → питання власнику щодо конфліктів (`AskUserQuestion`) → `--update --write` → тести й `ticket check` → коміт лише `write`.
- **Наслідки.** Рендер не змінюється - `PROCESS_VERSION` не піднімається. Проєкти без стану (project-a, project-b, project-c.lv) `--update` відхиляє; стан їм створює наявний bootstrap «Existing code» (уточнення до «Наслідків» ADR-028: файли, лишені через `--keep`, отримують `mode: keep` і далі `--update` їх не зливає). **Поза обсягом (E0-11):** злиття `keep`-файлів (база = поточний рендер); тут `--overwrite PATH` на `keep`-файлі - єдиний шлях взяти шаблон. *Зроблено в E0-11, див. ADR-038.* Відомо й прийнято: битий `settings.json` + `--keep` дає код 3 при кожному `--update` (розв'язується `--keep` щоразу); `.bak-<ts>` лишаються в дереві (`*.bak-*` у `.gitignore` проєкту й `filters.DENY_FILE_GLOBS`, не індексуються).

## ADR-036 Застарілий процес проєкту: проблема `process_outdated` при читанні й рядок у SessionStart

2026-11-12, planner E0-10; звірено з кодом docs-writer. Доповнює ADR-020, ADR-022, ADR-028.

- **Джерело - лише `scaffold.state.read(root)`** (ADR-028): проблема є тільки при `status = outdated` (`version < PROCESS_VERSION`). `none` (проєкт без стану), `current`, `newer`, `invalid` - без проблеми. Обчислюється при читанні, у БД не пишеться (як ADR-020), схема не змінюється.

Команда-підказка й фраза - константи `problems.UPDATE_CMD` / `UPDATE_PHRASE` (єдине джерело для UI і хука). Відкинуто: запис у `ticket_issues` під час refresh (watcher не бачить `.myvec/` - прихована тека, і стан застарів би після оновлення myvec без змін у проєкті).

Suggest to the owner: say "онови конвенцію"` - лише числа й фіксований текст. Лише основний checkout і без `agent_id` (дочірні сесії у worktree процес не оновлюють). `myvec.scaffold` (≈ 27 мс імпорту) імпортується лише коли `.myvec/scaffold.json` існує; будь-яка помилка - тиша, exit 0 (ADR-007). Відкинуто: окремий хук (ще один процес і ручний `install-hooks`) і рядок у `context.build` (обрізання `MAX_CHARS` могло б його з'їсти).
- **Обмеження:** вкладений підпроєкт (маркер `.myvector.toml` у підтеці, а `.myvec/scaffold.json` у корені репо) не отримує ні проблеми, ні рядка: стан шукається лише в `<root>/.myvec/`, де `root` - корінь самого проєкту. Це свідомо (рев'ю, Minor); лічиться окремо, якщо знадобиться.

## ADR-038 `scaffold --update` зливає файли `mode: keep` (3-way, як owned)

2026-11-12, E0-11 (звірено з кодом `scaffold/update.py`). Доповнює ADR-035 (знімає «Поза обсягом (E0-11)»), ADR-028.

- **Злиття:** keep-файл іде тим самим шляхом, що owned: ours = диск (`update._snap`), base = `files[rel].base`, theirs = новий рендер, `merge3`; дії `same`/`unchanged`/`update`/`merge`/`conflict`. База завжди є: стан пише `base` = рендер для кожного запису, зокрема keep (bootstrap `--keep`, `--update --keep`), а запис без `base` - `invalid`. Формат стану й `PROCESS_VERSION` не змінюються.
- **Відсутній / не звичайний / не UTF-8 keep-файл** - `keep` (не conflict): bootstrap `--keep` на `create` свідомо лишає файл не створеним; conflict тут блокував би кожне оновлення.
- **Конфлікт keep-файлу блокує запис (код 3)**, розв'язання - `--keep PATH` (мод `keep`, база = новий рендер) / `--overwrite PATH` (`.bak-<ts>`, мод `owned`). Обидва прапорці дозволені на будь-якому keep-файлі: `--keep` відхиляє чисте злиття, `--overwrite` бере шаблон. Автоматичні дії мод не змінюють. `--keep` на `same`/`unchanged` - no-op (мод лишається `keep`); `--overwrite` на `same` міняє лише мод на `owned` (файл не переписується), інакше `overwrite` з `.bak-<ts>`. Відсутній keep-файл власник видалив/не створював - автоматично не відтворюється ніколи; явний `--overwrite PATH` на ньому створює файл із шаблону (без `.bak`) - це задумано. Рядки keep-файлів у `--json` мають `"mode": "keep"` (skill рекомендує «keep mine»).
- **Відкинуто:** (B) «м'який» конфлікт keep-файлу - не блокує, база не рухається до явного `--keep`: менше питань власнику, але зміна шаблону висить непоміченою, стан потребує окремої бази на файл (зміна `build_modes`), а наступні чисті зміни того ж файлу теж не проходять; (C) лишити пропуск і брати шаблон лише `--overwrite` (стан до E0-11) - процесні виправлення ніколи не доходять до keep-файлів.
- **Наслідки:** у розгорнутих проєктах повністю свій keep-файл при зміні його шаблону майже завжди дасть `conflict` (одна відповідь власника на зміну, база рухається). Чисте злиття може внести шаблонний текст у «свій» файл - видно в перегляді, запис лише з `--write`.

## ADR-039 Окремий сервер ембеддингу для запитів пошуку (`query_url`)

2026-11-12, E8-09 (debugger, звірено з кодом `embed.py`, `config.py`). Доповнює ADR-029 (журнал пошуків), розділ README «Ембеддинги без Ollama».

- **Контекст (devbox, `logs/searches.jsonl`, 72 записи, лише агрегати):** p50 пошуку 10,1-10,3 с (daemon/direct/ui), розподіл кластеризований при 10,0-10,5 с; route: vector 43, hybrid 23, `fts-fallback` 5 (10,07 с = `QUERY_TIMEOUT`). `myvec search --debug`: embed query 4,4 с, пошук по БД ~0,3 с. Пряме `curl` у `/v1/embeddings`: 0,03-0,05 с, коли сервер вільний, 2-10 с під індексацією. Причина - head-of-line blocking в єдиному `llama-server` (`-np 4 -b 4096 -ub 4096`): запит стоїть у спільній черзі позаду батчів `embed_docs` (`batch_size = 16`), кожен decode на CPU під конкуренцією - секунди; кількість слотів не причина. Mac (Ollama) не зачеплений.
- **Рішення:** опційний `query_url` (за замовчуванням `""`). `Embedder.embed_query` іде на нього з `QUERY_URL_TIMEOUT = 2` с; при `EmbedError` - одна спроба на `ollama_url` (`QUERY_TIMEOUT` 10 с), далі як раніше `EmbedError` -> `fts-fallback`. `embed_docs` і запис пам'яті - лише `ollama_url`. Без `query_url` (або рівний `ollama_url`) нічого не змінюється. Контриб: `contrib/llama-embed/embed-query-server{,.service}` (127.0.0.1:11436, `-np 1 -c 2048 -b 2048 -ub 2048`). Встановлення - вручну власником.
- **Наслідки:** модель на query-сервері мусить бути тим самим файлом, що й в основному (інакше вектори розходяться мовчки; код не перевіряє). Fallback тихий - мертвий query-сервер видно лише як `embed query` ~2 с+ у `--debug`. Найгірший випадок 2 + 10 = 12 с до `fts-fallback` (замість 10). `query_url` читається на кожен запит демона. Пошук/RRF/модель не змінені, bench не потрібен. Ціль p50 < 1 с перевіряє live qa після встановлення сервісу.
- **Відкинуто:** (A) підняти `QUERY_TIMEOUT` - хвіст став би довшим, а агенти й так обирають grep; (B) пріоритетна черга в одному сервері - `llama-server` її не має, потрібен проксі/форк; (C) лише знизити `batch_size` (~4x менший decode) - зменшує, але не усуває чергу, CPU конкурує з VM; лишається як дешевий додатковий захід.

## ADR-040 Підказка «спершу myvec» у момент пошуку: хук PreToolUse `pre-search`

2026-11-12, planner E8-11 (чернетка, до затвердження плану). Доповнює ADR-029 (лог без тексту), ADR-031 (SubagentStart), ADR-007 (hooks). Джерела: internal report (unpublished), скрипт project-c.lv `myvec-first.sh` (урок 2026-11-12).

- **Канал - `myvec hook pre-search` на `PreToolUse`, matcher `Bash|Grep`**, синхронний, `timeout` 5. Вихід - лише JSON `hookSpecificOutput.additionalContext` (Claude Code кладе його system reminder-ом поруч із результатом інструмента); `permissionDecision` не ставиться - виклик ніколи не блокується і не переписується (`updatedInput` відкинуто: чужа команда, крихко). Glob не входить, поле `if` не використовується (рішення оркестратора).
- **«Нещодавно шукав» - власний стан хука, не `searches.jsonl`:** хук бачить у тому ж PreToolUse Bash-виклики `myvec search`/`recall` і пише час у `MYVEC_HOME/state/presearch/<session>-<agent>` (лише два числа: `searched`, `hinted`). Ключ - `session_id` (`SID_RE`) + `agent_id` (той самий фільтр, інакше `main`): субагент і головна сесія мають один `session_id`, а `searches.jsonl` агента не знає (ADR-029). Тиша 30 хв після `myvec search`, підказка не частіше 1 разу на 10 хв на (сесія, агент). Старі файли чистяться за `STATE_MAX_AGE` не частіше разу на годину (шлюз - mtime файла-штампа `state/presearch/.pruned`, не теки: кожен запис стану міняє mtime теки), файл сесії видаляється на `SessionEnd`.
- **Текст:** одне речення, фіксований ASCII-шаблон ≤ 300 символів із готовою командою `myvec search "<w1 w2 ...>"`, де слова - альтернативи/фраза з шаблону того самого виклику, лише `[A-Za-z0-9_.-]`, ≤ 6 слів по ≤ 40 символів (інакше `"<question>"`). Це відлуння власного вводу агента в його ж контекст, нікуди не пишеться; ADR-029 (жодного тексту в логах) не порушується. Відхід від ADR-031 «жодних даних зі stdin» свідомий і обмежений цим санітайзером.
- **Жодного тексту команди в логах:** розбір (`shlex`, regex) ловить винятки локально; у `hook.log` лише тип винятку без повідомлення й traceback-рядків з аргументами. Нічого не пишеться в журнал сесій (пульс і `session-event` не змінюються).
- **Швидкість:** stdlib, без `myvec.config`/`tomllib` на шляху «не пошук» (вихід після `json.loads` і regex-передфільтра); `config.home()` - лише коли треба стан. Ціль < 50 мс у процесі; виклик іде на кожен Bash, тож кожна мілісекунда множиться.
- **SessionStart/SubagentStart `SEARCH_HINT`** узгоджується з правилом власника (2026-11-12): `myvec search` першим для будь-якого пошуку, ідентифікатори теж; grep/rg - точні рядки в уже знайдених файлах і повний підрахунок. Обмеження ADR-031 (ASCII, ≤ 300, без даних) лишаються.
- **Наслідки.** Власник повторно запускає `myvec install-hooks` на обох машинах. Ефект міряється `myvec searches` (база - день розкатки, повтор через 14 днів); класифікатор «розвідувального» пошуку - чиста функція, яку може перевикористати E8-10 (знаменник). Ранжування, схема БД, `filters.py`, bench не змінюються.


## ADR-042 Чесний знаменник метрики «myvec проти grep»: відлік і чужа ОС при читанні, підвид self-пошуку - мітка при збиранні

2026-11-12, E8-10 (прийнято; частина A реалізована, частина B - тікет E8-16, ще не зроблена). Оркестратор: частина B винесена в тікет E8-16; `exact` лишається у знаменнику. Доповнює ADR-029 (`tool_calls`, `searchstats.usage`), ADR-037 (картка, `/api/search/usage`), ADR-013 (білий список `tokens.db`).

- **Контекст:** `tool_calls` зберігає лише `tool_id, file_id, ts, seq, cat, cwd`; `cat` = `self|myvec|recall`, команда не зберігається. Тому розвідку, grep в 1-2 відомих файлах, логи/tmp і find за іменем з наявних даних не розрізнити. На devbox 5 174 self-рядки мають cwd `/Users/…` (транскрипти Mac 22-31.10, до myvec) і йдуть у «(поза проєктами)» та в «усього».
- **Частина A - при читанні, без схеми і повністю ретроспективно (реалізовано, `searchstats.usage`):** (1) рядки з cwd чужої ОС (`/Users/` на Linux, `/home/` на macOS) не входять у частки, рахуються окремим лічильником `foreign`; (2) відлік проєкту `onset` = мін(`projects.registered_at`, перший `myvec`/`recall` виклик проєкту в `tool_calls`); рядки до відліку - лічильник `pre_onset`, не в частці; (3) `sessions_explore` / `sessions_myvec_explore`; (4) `p50_ms_24h` з `searches.jsonl` поряд із p50 за вікно. Мінімум у формулі відліку захищає від `rebuild`, який ставить `registered_at` = час перебудови. Дати встановлення хуків ніде не записано - не використовується. Префікс чужої ОС - `searchstats.FOREIGN_PREFIX` (`/Users/` на Linux, `/home/` на macOS); чужі рядки відкидаються до атрибуції й не впливають на `onset`. `--project` (`searchstatscli.resolve_project`): ім'я проєкту, `.` або наявний шлях (`realpath`, worktree через `sessions.project_of`); невідоме ім'я/неіснуючий шлях - код 1 (інакше опечатка перетворювалась на проєкт cwd), зареєстрований без викликів - нульовий рядок. Підвал картки (`ui/adoption.js`) без нових колонок.
- **Частина B (тікет E8-16) - мітка підвиду при збиранні:** нова nullable колонка `tool_calls.kind` з фіксованого переліку `explore|exact|file|logs|name` (для `cat=self`; для інших NULL). `tokens.classify` визначає її з `tool_input` тим самим проходом; зберігається лише мітка, не шлях, не шаблон, не команда. Міграція `tokens.db` v2 -> v3: `ALTER TABLE ADD COLUMN` + дочит транскриптів `gone=0` (`offset` -> 0), запис - upsert, що лише заповнює `kind IS NULL` (не перетирає `cwd`, переписаний `relocate`). Ретроспективність - лише на транскрипти на диску (~30 днів): рядки видалених транскриптів лишаються `kind NULL` = «некласифіковано», частка розвідки рахується по класифікованих і показує покриття. Уся ера myvec (з 03.11) ще на диску до ~03.12 - міграцію треба випустити раніше.
- **Знаменник основної частки:** `myvec / (myvec + self[explore])`; стара `share` (по всіх self) лишається в payload для порівняння. `exact` (один точний рядок по дереву) входить у знаменник (рішення оркестратора); з нього виводяться лише `file`, `logs`, `name`. У частині A знаменник - усі `self` після фільтрів чужої ОС і відліку.
- **Відкинуто:** (1) підвид у значенні `cat` (`self.explore`) - та сама міграція й дочит, але міняє зміст наявного поля для всіх читачів (`_misses`, `usage`) і старих збірок; (2) класифікація при читанні з транскриптів на вимогу - суперечить ADR-037 (без сканування транскриптів у API), повільно, зникає через 30 днів; (3) лише фільтри A без підвиду - знаменник лишається завищеним (60 % grep у відомих файлах).
- **Сумісність:** v3 читається старою збіркою (явні колонки, `kind` лишається NULL для її записів); дві машини мігрують незалежно. Payload `/api/search/usage` лише розширюється новими агрегатами (нових текстових полів нема). Ранжування й `bench/` не змінюються.
- **Доповнення E8-16 (2026-11-12, прийнято оркестратором; включає E8-07):** (1) перелік `kind` - `logs|count|file|explore|exact|name` з пріоритетом у цьому порядку; `count` (`-c`, `| wc`, Grep `output_mode: count`) поза знаменником, як `file`/`logs`/`name` (повний підрахунок - законне використання grep); нерозбірне - `kind NULL`. Записуються лише літерали зі списку (`searchkind.KINDS`), не текст команди. (2) Ортогональна ознака `tool_calls.doc` 0/1 (ціль або glob із `DOC_EXTS`) і новий `cat = 'read'` лише для Read файла з `DOC_EXTS` - метрика doc-читань проти `myvec search --kind docs` (`searches.jsonl` `kind`); шлях не зберігається, Read інших файлів не пишеться; старі читачі пропускають невідомий `cat`. (3) Класифікатор - чистий `searchkind.py` на парсері `presearch` (ADR-040) **без звернень до ФС** (для дочиту історії стан ФС інший); `DOC_EXTS` переїжджає в `searchkind`, `search` реекспортує. (4) Знаменник `share_explore = myvec / (myvec + explore + exact + некласифіковані)`: некласифіковане рахується як розвідка, тож частка - нижня межа без порогу покриття; покриття `classified` показується окремо, а `myvec searches` завжди друкує рядок «некласифіковано: N» окремо від решти підвидів. UI лише міняє знаменник у наявному стовпці (`share_explore`, а за його відсутності - стара частка) і дає `title`. (5) Міграція v3 одна для `kind` і `doc` (один повний дочит, а не два); upsert заповнює лише `kind IS NULL AND doc IS NULL` (`cwd`, `ts`, `seq`, `cat` не чіпає). (6) Read-only з'єднання з ще не мігрованою v2 `tokens.db` не падає: `_tool_rows` перевіряє `PRAGMA table_info` і читає `NULL AS kind, NULL AS doc` - self стають некласифікованими, лічильники лишаються. (7) Рядки `read` проходять ті самі фільтри `foreign`/`pre_onset`, тож ці лічильники включають і Read доків. Відкинуто: `doc` як мітка `kind` (губить підвид), друга копія правил розбору в `tokens.py`, частка лише по класифікованих (завищення при низькому покритті).

## ADR-043 Стислий вивід `myvec search` для агентів: авто за tty, підсумок ідентифікатора, кілька `-q`

2026-11-12, E8-13 (прийнято, реалізовано). Причини 5-6 звіту internal report (unpublished): відповідь 4-6 КБ проти сотень байтів grep, grep дає всі входження, агенти пакують 3-5 grep в один Bash.

- **Формат обирає tty:** stdout не tty (Bash агента) → стислий `path:start-end symbol` до k рядків без сніпетів і балу; tty → як раніше. `--compact`/`--expand` перебивають, `--full` ⇒ розгорнутий, `--json` і `--by-project` без змін. Відкинуто: лише прапорець (правило до агентів не доходить, причина 1), стислий для всіх (люди втрачають сніпети).
- **Демон:** поле `compact` у `/api/cli/search`, дефолт `false` (UI і старі клієнти без змін); ехо `compact: 1`, без нього клієнт іде прямим шляхом (як `cross`).
- **Ідентифікатор (один токен):** рядок `total in index: N lines in M files (word/prefix matches) · all: rg -n -F -- '<q>' <root>` (для одного слова ≥ 3 символи, не `kind=memory`, не `--by-project`); N - унікальні `(repo, path, рядок)` по FTS-кандидатах (останній токен - префікс `"tok"*`) із точним підрядком (чанки перекриваються), гілка/`docs` фільтруються до межі 5000 → `≥`. Збіг усередині довшого слова (camelCase) FTS не бачить - мітка чесно каже «word/prefix», повний підсумок дає `rg`. Рядок додається лише коли викликач просить `total` (CLI завжди; UI `/api/search` ні). Лише в stdout; для запиту з hard secret без `rg`; запит у логи не пишеться (ADR-029).
- **Кілька запитів:** `-q` повторюваний (≤ 5), кожен - окремий пошук і окремий запис у `searches.jsonl`; поле `fmt` у журналі - прапорець формату, не текст.
- **Не змінюється:** `search()`, скоринг, роутинг (bench не переганяється), схема БД, `filters.py`, `hooks.SEARCH_HINT`, `presearch.HINT_TEMPLATE`, шаблони scaffold.

## ADR-044 Прибирання реєстру: `myvec forget-project` з dry-run, без автоприбирання

2026-11-12, E8-15 (прийнято, реалізовано). Доповнює ADR-021/028 (рендер qa-шаблону, `PROCESS_VERSION` 4).

- **Контекст:** `register_root` лише дописує, `rebuild` мовчки пропускає відсутні корені, видалення проєкту нема. На devbox у реєстрі 21 з 39 коренів - worktree, усі відсутні на диску; 4 рядки `projects` з відсутнім коренем тримають 68 рядків тікетів, які демон ніколи не оновить. `gc` уже видаляє repo зниклої теки, але не проєкт, тікети й реєстр.
- **Рішення:** команда `myvec forget-project [TARGET] [--missing] [--yes]`; без `--yes` лише звіт. Стан кореня: `present` / `gone` (теки нема, батьківська непорожня; для `.worktrees/<id>` - основний checkout непорожній) / `unreachable` (нема батьківської або вона порожня чи нечитабельна - порожня тека може бути точкою монтування відключеного диска; чужа ОС, видалене дерево). `--missing` бере лише `gone`; `unreachable` і `present` - лише явною ціллю. Запис під `sync_lock`: repos (`drop_repo`), тікети (`tickets*`, `ticket_dirs`), рядок `projects`, корінь у реєстрі, сироти - спільна з `gc` функція. Не чіпає дочірні проєкти, пам'ять/vault, історію сесій/прогонів/токенів, маркер. `status` і `gc` друкують рядок-підказку, коли є відсутні корені. qa прибирає свій tmp-проєкт `forget-project --yes`.
- **Відкинуто:** (A) автоприбирання в демоні/`gc` - відсутній корінь не відрізнити від незмонтованого диска чи індексу, скопійованого з іншої ОС до `relocate`; (B) автоприбирання worktree за `git worktree list` - сильний сигнал, але запис без згоди й git-процес у фоні; (C) каскад на дочірні проєкти за префіксом - worktree-проєкти дочірні до основного, помилкова ціль знесла б багато.
- **Сумісність:** схема БД не змінюється; `forget-project` міняє лише похідні дані (`rebuild` для `present` кореня з маркером поверне проєкт). Дві машини прибираються незалежно.

## ADR-046 Оновлення прийнятого `search.md`: лише байтовий збіг зі старим рендером

2026-11-12, E8-17 (прийнято). Доповнює ADR-041 (`--adopt` без стану), ADR-045 (`search.md` v5), ADR-023 (транзакція `apply`).

- **Контекст:** `--adopt` не пише стан, тож після зміни шаблону (E8-14) прийнятий файл став `foreign` і не оновлюється; 5 проєктів лишились на тексті v3.
- **Рішення:** у `problems.py` (stdlib) реєстр `SEARCH_RULE_OLD` = sha256 сирих байтів кожного старого рендеру -> перша `PROCESS_VERSION`. Повторний `--adopt`: файл, чий відбиток плану (`pl.fp`, sha256) є в реєстрі, - дія `update` (з `--write` - `apply` з overwrite, відбиток захищає від гонки); будь-який інший - `foreign` з підказкою злити вручну (симлінк на шляху - не `foreign`, а код 2, ADR-041: його не читають і не слідують). Стан не пишеться. Код проблем `search_rule_outdated`. Тексти старих версій лише в тестових фікстурах; тест-сторож вимагає запису історії при кожній зміні шаблону.
- **Відкинуто:** повні старі шаблони у wheel (мертвий текст у пакеті); маркер версії у файлі (нема в розкатаних файлах, правка з маркером виглядала б чистою); стан на один файл (ADR-041, A); нормалізація пробілів/CRLF перед порівнянням (будь-яка різниця - можлива правка власника).
- **Наслідки:** зміна `search.md` тепер вимагає додати хеш попереднього рендеру й фікстуру; `PROCESS_VERSION` для цього не піднімається.

## ADR-047 Протокол нода ↔ хмара v1: снапшот і події, токен ноди, білий список команд, ключ проєкту за remote

2026-11-12, E4-01 (запропоновано). Доповнює ADR-001 (хмара на pm.example.com). Лише протокол: коду, деплою й акаунтів немає; реалізують E4-02, E4-03, E4-06, E4-07.

- **Контекст:** ADR-001 фіксує архітектуру (Worker + D1 + Durable Object, вихідний WS ноди, назовні лише тікети й сесії, з хмари - білий список, вхід Access, bearer-токен, проєкт за git remote), але не формат обміну. Протокол перевикористовує наявне: маскування тікетів (ADR-005), рядки сесій (ADR-007/ADR-009), дії над сесією (ADR-010/ADR-014), inbox (ADR-019/ADR-027), приватність (ADR-013/ADR-029/ADR-030).
- **Транспорт.** Лише нода ініціює: `wss://<host>/node/v1/ws`; демон слухає тільки 127.0.0.1, вхідних портів нема. HTTP-фолбек `POST /node/v1/snapshot` (повний снапшот одним тілом); команди лише по WS (без WS нода для хмари read-only). Клієнт - окремий фоновий потік демона (як семплер, ADR-012): збій хмари не гальмує тік, sync, пошук; бекоф 1 с -> 5 хв із jitter.
- **Конверт.** `{"v": 1, "type", "seq", "ts", ...}`; `v` - мажорна версія; невідомі поля ігноруються обома сторонами (додавання без бампу), невідомий `type` -> `error`, з'єднання живе. Ліміт повідомлення 512 КіБ (межа WS у Workers 1 МіБ), більше - ділиться на частини. Перше повідомлення - `hello {node, myvec_version, protocol: 1, caps}`, відповідь - `welcome {server_time, resync: true}`.
- **Снапшот.** Після `welcome` і на кожен `resync` нода шле повний стан із поколінням `gen`: `snapshot.begin {gen, projects}` -> `snapshot.project {gen, project, part, parts, tickets[]}` і `snapshot.sessions {gen, sessions[]}` -> `snapshot.end {gen}`. Worker застосовує покоління атомарно лише після `end` (незавершене відкидає), замінюючи все, що мав від цієї ноди: снапшот ідемпотентний.
- **Події.** `tickets.project {project, fingerprint, tickets[]}` - повна заміна тікетів одного проєкту при зміні відбитка (як ADR-005); `session.upsert`, `session.remove`; `project.remove {project}` - проєкт зник із вивантажуваного набору (`shared = false`, `forget-project`, зникла тека тікетів, інший remote): Worker видаляє його тікети й сесії; сама зміна набору проєктів (маркер, `init`/`forget-project`) також запускає новий снапшот, щоб прибрати залишки; `heartbeat` раз на 30 с. `seq` зростає в межах з'єднання, Worker відповідає `ack {seq}`; пропуск `seq`, невалідна подія чи рестарт DO -> `resync`.
- **Що виходить (білий список полів).** Тікети: `id, title, kind, status, parent, size, deps, blocks, branch, pr, summary, updated`, відсоток, `body_sections` - уже масковані (ADR-005); нода маскує ще раз на виході (`filters.mask_secrets`, як `testruns._shape`) і викидає поле з hard secret; inbox - лише кількість на тікет. Сесії (форма `_sessions_payload`, ADR-007/ADR-009): `session_id`, `project`, `effective_state`, `last_seen`, `last_state_event_at`, `wait_s`, `ticket_id`, `ticket_source`, масковані питання/варіанти/хвіст відповіді, `mode`, `answer_kind`; `cwd` лише відносно `$HOME` (`~/...`). **Ніколи:** код і чанки, вектори, пам'ять/vault, `searches.jsonl`/`queries.jsonl` (ADR-029), `tokens.db` і транскрипти (ADR-013), `load.db` (E6-08 - окремий ADR), текст промптів і текст команд з хмари. **Проєкт із `shared = false` (ADR-030, fail-closed) у хмару не вивантажується взагалі**, ні тікети, ні сесії; зіпсований маркер = прихований. Фільтр - як `crossproject.hidden_projects(db, ctx=None)` (ctx=None: без винятку «своя родина», бачить себе лише власник локально; уся родина), не одиночний `is_shared(root)`: вкладений підпроєкт під `shared = false` батьком теж прихований, навіть без власного маркера.
- **Автентифікація ноди.** Токен на ноду: 32 випадкові байти (base64url); у D1 лише SHA-256 і ім'я `node`; `node` у `hello` мусить збігатися з прив'язаним, інакше 4403. Токен лише в `Authorization: Bearer` (WS upgrade і фолбек), ніколи в URL/query. На ноді - файл `MYVEC_HOME/state/cloud.token` (`0600`), **не в `config.toml`** (config показують і копіюють між машинами); у config лише `[cloud] url, node, enabled, commands`. До двох активних токенів на ноду (ротація без простою), відкликання = видалити хеш. Браузер: Cloudflare Access на всьому, крім `/node/*`; `/node/*` поза Access, лише bearer; Worker додатково перевіряє JWT Access (`Cf-Access-Jwt-Assertion`) на браузерних маршрутах. Коди закриття WS: 4400 невідома версія/зламаний конверт, 4401 нема/невалідний токен, 4403 відкликаний або чужа нода, 4409 замінено новим з'єднанням тієї ж ноди (E4-06), 4413 завелике повідомлення.
- **Команди з хмари (білий список v1).** `cmd {cmd_id (UUID), name, args, issued_at, expires_at}`: `ticket.comment {project, ticket_id, text}` -> `inbox.write(kind="comment", source="cloud")`; `ticket.status {project, ticket_id, requested_status, text?}` -> `inbox.write(kind="status", source="cloud")` (тікет нода не редагує, статус міняє оркестратор, ADR-019); `session.resume {session_id, text | option + question_at + label}` -> той самий шлях, що `POST /api/sessions/{sid}/resume` (ADR-010/ADR-014: `cm who` авторитетно, `held`/`busy` -> відмова, текст лише stdin); відповідь варіантом без `question_at` -> 400; розбіжність `question_at` з поточним питанням сесії або відсутній/інший `label` при наявних варіантах -> 409 (як локальний POST: відповідь не йде на застаріле питання). Нода виконує тими самими функціями, що й локальні POST (одна реалізація), з тими самими перевірками: ім'я поза списком -> `rejected/unknown_command`; невідомий `project`, id не з `tickets`, sid не UUID або не з `sessions` ноди -> 404; **команди дозволені лише для проєктів і сесій із вивантаженого набору** (shared, не нащадок прихованого, див. «Що виходить»): `project`/`session_id` поза ним -> 404 як невідомі, ключ `git:...` вгадати не дає доступу до прихованого проєкту; ліміти тексту (inbox 4000, send 16000), керівні символи, hard secret -> 400; `expires_at` минув -> `expired`; `cmd_id` записується в кеш (`state/`, TTL 24 год) **до** виконання зі станом `in_progress`; повтор `cmd_id` -> збережений результат без повторного виконання, а запис `in_progress` без результату (крах ноди між `cm send` і записом результату) -> `failed`, не повтор (at-most-once, краще втрата, ніж дубль тексту в сесії). Нода відкидає команду статусом `rejected` (code 400), якщо `expires_at - issued_at` > TTL кешу (24 год) або `issued_at` у майбутньому понад допуск годинника (5 хв): команда не переживе витіснення `cmd_id` з кешу. `cmd_result {cmd_id, status: done|rejected|expired|failed, code, message ≤ 300 символів, масковане}` без тексту команди. Текст ніде не логується (у `bus` лише довжина); Worker тримає його лише до доставки/`expires_at` (E4-07). **`[cloud] commands` за замовчуванням `false`** (лише вивантаження), вмикає власник явно (E4-05). `source = "cloud"` додає клієнт E4-03 в `inbox`.
- **Ідентичність проєкту.** `project` = `git:<host>/<owner>/<repo>` з remote `origin` (або першого) основного checkout: `ticketops.sanitize_remote` (без userinfo), host у нижньому регістрі, без `.git` і кінцевого `/`; scp-форма, `ssh://git@host[:port]/o/r` і `https://host/o/r` дають один ключ. Вкладений проєкт - `git:<...>#<шлях від кореня репо>`. Без remote - `local:<node>:<шлях відносно $HOME>`. Worktree окремим проєктом не вивантажується: тікети з основного checkout (ADR-005), сесії з worktree - до проєкту основного (`project_of`). Remote читається з `.git/config` при зміні його mtime, без git-процесу на тік.
- **Свіжість між нодами.** Проєкт на кількох нодах - одна картка. Нода шле `fingerprint` (sha256 відсортованих `(id, status, updated, title, sha тіла)`), `head` (sha, `committer time`, гілка), `dirty` (незакомічені зміни в теці тікетів), `tickets_mtime`. Свіжість ноди = `max(head_time, tickets_mtime, якщо dirty)`; картка показує версію найсвіжішої ноди цілком (відсотки груп і дерево лишаються цілісними). Відбитки різні -> позначка «розбіжність» з нодами, їхніми `head` і списком id з різним статусом (рахує Worker); однакові - без позначки. Хмара нічого між нодами не синхронізує: джерело істини - git (ADR-001), розбіжність знімає `git pull/push`.
- **Відкинуто:** (A) журнал подій із реплеєм - стан ноди повністю в БД, снапшот дешевий; (B) довільні команди, shell, прямий запис у тікети, git-операції з хмари; (C) токен у `config.toml` або в URL - config копіюють, URL потрапляє в логи; (D) окремий ключ маркера `cloud = false` замість `shared = false` - два прапорці приватності розходяться, `shared` уже fail-closed; (E) хеш remote як ключ - назва репо й так видна в картці, ключ без хешу дебажиться; шлях як ключ для проєктів з remote - Mac `/Users/...` і devbox `/home/...` різні; (F) свіжість за `updated` окремого тікета (змішане дерево) чи за часом снапшоту (devbox без змін «свіжіший» за Mac з новими коммітами).
- **Не робиться в E4-01:** код Worker і клієнта, деплой, акаунти, DNS, Access-політики й токени (E4-05, за згодою власника), метрики навантаження/прогонів (E6-08), багатокористувацький доступ. Схема `index.db` не змінюється.
- **Наслідки:** старі ноди без клієнта просто не з'являються; мажорний бамп `v` - Worker закриває 4400 з підказкою оновити myvec; якщо реалізація впреться в ліміти Workers/D1 - ADR уточнюється окремим пунктом «уточнено», не мовчки.

Приріст скромний, вибірка мала; «docs випереджають код» - окрема проблема, не вирішена.

## ADR-050 Worker v1 локально: HTTP-снапшот, правило `gen`, схема D1, мінт токена, read API fail-closed

2026-11-14, E4-02 (прийнято, звірено з реалізацією). Уточнює ADR-047 (пункт «уточнено» для HTTP-фолбеку), доповнює ADR-001. Лише локально: `wrangler dev` + vitest (`@cloudflare/vitest-pool-workers`), без деплою й акаунтів (E4-05).

- **Контекст:** ADR-047 каже «HTTP-фолбек шле те саме одним тілом», але не фіксує форму тіла, відповідь, порядок поколінь, ліміти й зберігання; E4-03 (клієнт) і E4-06 (DO) спираються на ці деталі.
- **HTTP-снапшот.** `POST /node/v1/snapshot`, `Authorization: Bearer`, тіло `{v: 1, type: "snapshot", gen, ts, node?, projects: [{project, fingerprint, head{sha,time,branch}, dirty, tickets_mtime, tickets[]}], sessions[]}` ≤ 8 МіБ (інакше 413; WS-ліміт 512 КіБ на повідомлення не змінюється). Відповідь `{v:1, type:"snapshot.ack", gen, projects, tickets, sessions}`. Помилки - JSON `{error}` (для схеми ще `field` - шлях без значення): 400 (схема, `v != 1`, оборонна перевірка PEM/AKIA), 401 (нема/невалідний токен), 403 (`node` ≠ прив'язаному), 409 `stale_gen`, 413, 415. Ліміти (константи в `schema.ts`): 200 проєктів, 5000 тікетів на проєкт (20000 усього), 2000 сесій, рядок <= 16 КіБ, JSON-поле (`body_sections`, `question_options`) <= 256 КіБ, серіалізований `data` рядка тікета/сесії <= 1 МіБ (`MAX_DATA_BYTES`, нижче ліміту рядка D1 ~2 МБ; більше -> 400 `invalid_field` зі шляхом, не 500); дублікат id/session_id/проєкту -> 400. Оборонна перевірка PEM/AKIA іде по сирому тілу і по `JSON.stringify` розібраного (ескейпи `\\u0041` не обходять), не замінює `filters.py` ноди.
- **`gen`.** Worker зберігає `nodes.last_gen`: менший -> 409, рівний -> 200 без запису (ідемпотентний повтор), більший -> атомарна заміна всіх даних ноди однією транзакцією D1 (`batch`). Гонка двох паралельних запитів закрита всередині batch: першим іде `UPDATE nodes SET last_gen ... WHERE last_gen IS NULL OR last_gen < ?`, а DELETE і `INSERT ... SELECT` умовні (`(SELECT last_gen FROM nodes WHERE name = ?) = ?`), тож запізнілий менший gen нічого не змінює (відповідь 409 за повторним читанням); попередній SELECT лишається швидким шляхом і тримає рівний gen без запису. Нода мусить тримати `gen` монотонним і між рестартами (рекомендовано unix ms) - контракт для E4-03.
- **Зберігання.** D1: `nodes`, `node_tokens(token_hash = hex SHA-256 UTF-8 рядка токена, node)`, `node_projects`, `tickets(node, project, id, kind, status, parent, data JSON)`, `sessions(node, session_id, project, data JSON)`. У `data` лише поля білого списку ADR-047 (тікет: `id, title, kind, status, parent, size, deps, blocks, branch, pr, summary, updated, progress, body_sections, inbox`; сесія: `session_id, project, effective_state, last_seen, last_state_event_at, wait_s, ticket_id, ticket_source, title, question, question_at, question_options, last_message, mode, answer_kind, cwd`), невідомі відкидаються (додавання поля = зміна білого списку Worker). Сирого токена в D1 нема; після пошуку за хешем збережений хеш ще порівнюється сталочасно (`crypto.subtle.timingSafeEqual`). Злиття проєкту між нодами й «розбіжність» - при читанні (E4-04), у D1 рядки по нодах.
- **Мінт токена (dev).** `cloud/scripts/mint-token.mjs --node --out`: 32 байти base64url лише у файл `0600`, у D1 (`--local`) лише хеш; ≤ 2 активних на ноду (третій - відмова з кодом 3, `--revoke-oldest` знімає найстаріший). Адмін-HTTP для мінту нема (нема поверхні атаки); віддалений мінт - E4-05.
- **Read API.** `GET /api/v1/{nodes,projects,tickets,sessions}`, без `token_hash`. Fail-closed: 403, доки не перевірено Access JWT (E4-05); локальний обхід лише `ACCESS_DEV_BYPASS = "1"` **і** hostname `localhost`/`127.0.0.1`. Змінної **нема в `wrangler.toml`** (за замовчуванням вимкнено, `[env.dev]` не потрібен): вмикається `--var` у `npm run dev` або gitignored `cloud/.dev.vars`; тести ставлять її по кейсу, є тест 403 без обходу.
- **Тести.** `uv run pytest -q` лишається Python-only зі статичним сторожем `cloud/` (точні версії, `.gitignore`, нема `account_id`/routes); vitest - окремо `npm test` у `cloud/`, послідовно (пам'ять devbox).
- **Відкинуто:** (A) pytest-обгортка над `npm test` - workerd на кожен прогін і мовчазні скіпи; (B) JWT Access уже в E4-02 - без реальних team domain/AUD, +обсяг; (C) колонки під кожне поле тікета - білий список міняється частіше за схему; (D) токен у stdout мінту - потрапляє в історію/логи; (E) адмін-ендпоінт мінту - зайва автентифікація до Access.
- **Інструменти:** точні версії, `package-lock.json` у git; `@cloudflare/vitest-pool-workers` 0.23.0 уже позначений як перейменований у `@cloudflare/vitest-plugin` (міграція - окремо); `npm install` на npm 10 падає (arborist, peer set), lock оновлюється `npx npm@11`, `npm ci` на npm 10 працює.
- **Наслідки:** E4-03 шле `gen` = unix ms і тіло цієї форми; E4-05 додає JWT у `requireBrowser`, не вмикає `ACCESS_DEV_BYPASS`, мінт `--remote`; E4-06 використовує ту саму функцію атомарної заміни для WS-снапшоту.
